## Context

V5 目前是“V3 物化 + V5 语义/布局/质量后处理”的复合编译器。复用本身不是问题，问题在于内部 V3 页面通过公共进度通道泄漏，且调用方依靠 `story_plan is not None` 隐式选择版本。这样会出现三个不一致的事实：页面顶部写着 V5，实时预览是 V3 基础页，最终是否有 V5 候选则要等任务结束后才知道。

本变更面向来源静态、输入合法且基础设施健康的课程，保证产出完整、可编辑的 V5 候选。它不承诺每一页自动达到最终美术质量；页面级视觉异常可进入人工修改态。模型服务、存储、渲染器不可用，生成期间来源改变，或出现未知数据损坏时仍应明确失败。

## Goals / Non-Goals

**Goals:**
- 对静态合法课程保证一个完整、可阅读、可编辑的 V5 候选。
- 消除 V5 构建过程中的 V3/V4 可见降级和静默降级。
- 完整保留来源片段的处置证据，不静默丢内容。
- 区分可人工修订的页面问题与必须中止的系统问题。
- 让浏览器、导出器、质量门禁和任务状态使用同一最终页面契约。

**Non-Goals:**
- 保证零人工修改或保证每次都达到最高视觉评分。
- 删除历史 V3/V4 课程或禁止其继续查看、编辑和导出。
- 将任意不可解析、损坏或生成中变化的课程伪装成成功。
- 把安全页面硬限制为三页并因此截断来源。

## Decisions

### Decision: 目标 schema 由任务显式传入，不能再由 `story_plan` 是否为空推断

任务在开始时固定 `requested_schema` 和源修订。V5 调用必须经过 V5 专用闭合分支，并在提交前断言产物 schema 为 `slide_deck_v5`。旧版入口可继续服务历史构建，但不能成为 V5 的异常分支。

### Decision: V3 只作为 V5 内部物化实现，不拥有公共候选事件

V5 可以继续复用稳定的 V3 分块、练习关联和基础页构造，但其 `slide_upsert` 只在编译器内部流动。V5 完成语义、最终布局、来源处置和质量契约后，先发 `slide_reset`，再发送带 `engine_schema=slide_deck_v5`、`candidate_stage=final_contract` 的页面事件。前端在目标 V5 任务中拒绝缺少这些字段的旧版页面事件。

### Decision: 使用三终态，而不是以旧版作为兜底

- `v5_ready`：全部发布门禁通过，无需人工修改。
- `v5_needs_manual_edit`：内容完整且可阅读，只有页面级非阻塞问题，用户可以编辑后重新校验。
- `v5_failed`：源契约、源修订、基础设施、导出/渲染完整性或未知回归等全局失败。

表示记录仍可使用现有生命周期状态；V5 终态写入内容/质量摘要并由 API 显式返回。`v5_needs_manual_edit` 是可发布的完整候选，不是降级版本。

### Decision: 超容量来源使用 V5 安全页面和确定性续页

安全页面优先忠实表达源内容，使用受支持的最终布局、保守字号和可预测分栏/续页。目标是 1–3 页展示一个异常来源单元；若三页不足以完整覆盖，必须继续分页并记录原因，禁止截断。每个来源片段最终处置只能是：`rendered`、`rendered_in_safe_layout`、`moved_to_appendix`、`needs_manual_edit`、`intentionally_excluded_with_reason`。

### Decision: 页面级异常与全局失败使用明确分类

确定性修复穷尽后，如果页面仍完整可读，转为安全布局并记录 `manual_edit_required`。缺内容、文字不可读、缺最终布局、导出失败、来源修订改变、存储/模型/渲染基础设施不可用和未知异常均为硬失败。失败信封至少包含 `stage`、`code`、`message`、`retryable`、`source_revision`，以及可用时的 `chapter_id`/`page_id`。

### Decision: 最终布局是 V5 唯一渲染依据

浏览器和 PPTX 导出器对带 V5 最终页面契约的页面只读取 `quality.resolved_layout`。缺失或不受支持时，质量门禁必须阻止发布；渲染器不得回退到 `requested_layout` 或旧 `layout`。V3/V4 历史内容保留兼容逻辑。

### Decision: 原子提交并保留 last-good

构建、修复、最终渲染审计、来源处置审计全部在影子候选中完成。只有 `v5_ready` 或 `v5_needs_manual_edit` 才原子替换当前 V5 候选；`v5_failed` 保留上一个可用版本并返回失败信封。

## Risks / Trade-offs

- [最终 V5 事件晚于旧实时预览] -> 通过阶段进度、章节计数和修复状态保持反馈；不再展示语义不真实的 V3 页面。
- [安全页面增加页数] -> 以完整性优先，并把异常来源单元的目标控制在 1–3 页，超出时记录诊断。
- [人工修改候选被误解为完全通过] -> UI 同时展示候选终态、问题页数量和逐页修改原因。
- [前后端滚动发布期间事件协议不一致] -> 后端先兼容发出明确事件信封，前端仅对声明目标 V5 的任务启用严格过滤；部署在同一发布流程完成。
- [新失败门禁暴露历史隐患] -> 保留 last-good，并提供稳定错误代码与可重试标识，禁止无提示回退。

## Migration Plan

1. 增加协议模型和兼容读取，不改变历史 V3/V4 数据。
2. 增加回归测试并验证当前代码确实泄漏 V3 事件/允许隐式分支。
3. 后端实施显式 V5 分支、事件隔离、安全候选和结构化失败。
4. 前端实施 V5 事件过滤、候选终态和人工修改/失败展示。
5. 执行后端、前端、E2E、PPTX 渲染和生产就绪审计。
6. 合并到 `main`，由生产工作流部署；完成线上 V5 构建、预览、任务轮询和导出冒烟。

回滚时整体回退此发布，保留上线前 last-good 表示；不得通过重新启用 V5→V3 降级来掩盖故障。

## Observability

- 记录 V5 构建终态及 `failure.code`。
- 记录安全页面数、人工修改页数、来源处置分布和超出三页的来源单元数。
- 记录被隔离的内部 V3 页面事件数量；公共 V5 候选事件若出现非 V5 schema，立即告警。
- 生产冒烟至少断言目标、候选、发布 schema 均为 V5，且导出成功。
