# 师生一体课程开发分析

分析日期：2026-09-28。代码基线：`ea98294fc1ffc242208dc311e6d60476799746bc`。

这是团队开发参考，保留原分析中的项目对象、源码发现、设计建议、实施次序和验收要求，已移除私人语料及其引用。建议不等于已批准需求，基线发现不等于最新状态；实施前重新核对代码。现行产品定义见[产品逻辑设计](../../产品逻辑设计.md)、[教学内容设计](../../教学内容设计.md)、[交互与界面设计](../../交互与界面设计.md)及[产品状态](../../产品状态.md)。

随附[后端依赖核查](后端依赖核查.json)是原基线的静态检查结果，不代表本次清理重新运行了后端验收。

## 一、核心判断：有基础，也有需要共同补齐的关系

这次建设的目标，是在同一课程产品中同时做好教师备课与学生学习。教师端保留现有设计和已经形成的生成、编辑、文件管理能力；学生端恢复以课程学习为中心的完整使用流程，并配套笔记、练习、错题和 AI 辅导。知识图谱暂不进入本轮建设范围。

现有后端已经拥有课程内容、资料处理、教案与讲义生成、题库、正式作答、学习记录、AI 老师、任务与恢复等能力。学生端需要的多数功能能够找到对应实现，其中一些已经增加了修订检查、学习事实记录、持久任务和失败恢复。因此，后续开发应继承这些成果。

但能力存在，并不等于各项能力已经按照师生一体的产品关系组织好。目前，新课程生产只接受教师模式，普通课程列表排除教师课程，正式身份接入默认只允许教师和管理员，教师预览中的学习操作也特意不写正式记录。恢复旧学生页面，无法自动改变这些约定。

另一方面，本次实际运行后端依赖检查，发现 333 个生产模块中存在一组涉及 12 个模块的循环依赖。任务管理与课程生成两个核心文件分别为 10,874 行和 9,988 行。这些事实说明：功能积累已经较丰富，职责与依赖仍需要整理。文件长度本身不证明功能失效；依赖检查失败也不等于已经出现线上故障，但不能再据旧文档宣称当前后端没有循环依赖。[C12]

本报告建议将接下来的工作确定为：

> 先明确完整产品中的对象、关系、操作与状态，再联动调整前后端；每项共有能力保持明确的责任和正式写入路径，教师与学生通过适合各自任务的界面使用它。

开发可以分阶段，阶段之间必须承接同一套设计。第一版可以控制功能范围，纳入范围的功能则要共同形成完整结果。课程创建、内容生成、阅读、笔记、练习、错题和恢复不能各自完成后，再把相互关系留给临时补丁。

## 二、产品方向与用词

### 2.1 已经明确的产品方向

本报告采用以下产品方向；具体实现仍以正式设计文档与实施决定为准：

1. 教师端现有成果值得保留，教师端与学生端共同建设。
2. 课程是两边共有的核心，课程生成所用的教学设计能力应当复用。
3. 教师除了课程本身，还需要教案、教学大纲、教学日历、评分标准等配套文件，常规填写和生成尽量一次完成。
4. 学生除了生成与学习课程，还需要笔记本、错题本等配套服务；知识图谱暂不做。
5. 学生端参考三月和七月版本的整体交互逻辑，教师端基本沿用当前设计。
6. 后续开发需要把有关功能联动、联合、有机地补齐，并使后端链路唯一、可用、干净、稳定。

这些是本报告的方向依据。教师与学生账号如何组织、共享课程采用哪个版本、学生生成是否需要完整教案等具体选择，尚未因上述方向而自动确定；第十一章分别给出建议与影响。

### 3.2 恢复的是功能关系

```text
我的课程：新建、导入、继续学习
                ↓
课程学习现场：目录 — 正文 — 笔记／AI 助手
                ↓
练习 → 作答反馈 → 错题记录 → 针对再练
                ↓
返回对应正文，继续原来的学习位置
```

目录帮助学生看清结构，正文承载理解，笔记与 AI 服务当前位置，练习检验实际运用，错题帮助再次学习。集中整理和就近使用需要同时成立：阅读侧栏负责当前内容，完整笔记本负责搜索、整理与导出；错题本负责从历史作答继续学习。

历史源码中的视觉装饰、早期身份处理、旧字段写入和已经退役的生成接口不随交互设计一起恢复。当前笔记保存、预览隔离和任务恢复等修复继续保留。三月代码提供交互参考，当前数据与服务承担正式实现。

### 4.1 能力核对

下表的“已有”指源码中存在相应接口和实现，不等于本轮完成了真实模型、完整页面或生产验收。

| 用户要完成的事情 | 已有实现 | 判断与需要共同处理的部分 |
| --- | --- | --- |
| 创建并生成课程 | 课程草稿、持久生成任务、课程规划、分讲教案和讲义 | 共有生成能力可复用；新任务在路由与任务管理中均被限定为教师模式，学生入口必须与后端条件一起调整 |
| 导入已有内容 | Markdown 解析、同步导入和持久任务导入 | 已有基础；两个公开入口需要确认调用者，统一归属、校验、保存与恢复 |
| 阅读课程 | `CourseDocument`、教师讲义的只读内容转换、课程读取接口 | 已有基础；需要明确学生可见范围、内容修订和旧课程读取关系 |
| 保存笔记和批注 | 学习记录创建、修改、归档、原文定位与修订检查 | 适合复用；与正文变化、跨端保存和删除后的引用状态共同验证 |

| 继续学习与复习 | 学习位置、快照、进度、继续学习与复习接口 | 已有；部分复习代码仍按旧二级节点取范围，需统一“哪些内容可以学习”的判断 |

| 学习情况判断 | 事件、正式记录、作答与 `LearnerModel` | 已有结构；长期有效性尚需真实学习样本，不能由界面统计代替 |

| 长任务与恢复 | 任务身份、工作区、检查点、容量调度和失败状态 | 值得保留；各类任务的自动或手动恢复规则需要明确，不能强行统一成自动重试 |

### 4.2 已查明的主要差距

**第一，产品约定已经偏向教师生产。** 当前《产品逻辑设计》明确将学生独立使用流程排除在上一轮范围之外，并规定教师工作台是唯一新课程生产入口。这与本次师生共同使用的目标不同。实现前需要更新对应章节，不能一边执行新要求，一边让旧约定继续决定生成、身份和验收范围。[产品逻辑设计](../../产品逻辑设计.md)

**第二，学生生成并非只缺一个按钮。** `POST /course-generation/generate` 对非 `lesson_assets_v1` 请求返回 410；任务管理器也再次拒绝旧生成模式，并校验教师草稿归属。新学生流程需要改变共有生成服务的输入与适用条件，同时保留现有教师行为。只改前端参数或只取消一处检查会留下不一致。[C1、C11]

**第三，课程可见范围与个人归属尚未形成统一的学生使用规则。** 普通课程列表排除教师课程，在该列表函数内没有按 `owner_id` 筛选个人课程。教师课程的部分读取和写入检查位于具体路由；通用 `get_course_or_404` 主要负责读取与不存在处理，本身不接收当前用户。由此可以确定，需要把课程访问规则检查到所有相关读取和写入入口；本次没有做完整越权测试，不把这一静态发现直接写成已验证的线上漏洞。[C1、C3]

**第四，开放学生身份会影响整个 API 边界。** 启智身份接入默认仅允许 `teacher/admin`，本地开发身份也不等同于正式登录。不能仅在允许角色中加入学生就结束；必须同时检查教师专用操作、课程所有权、个人记录以及 HTTP、SSE、WebSocket 的一致性。[C3]

**第五，正式学生使用与教师预览必须保持不同的数据行为。** 当前教师预览通过独立读取与试做接口，保持临时笔记和练习不写正式学习事实。这个设计需要保留。正式学生入口则必须保存本人记录，不能因复用预览而出现“页面能用，但学习结果没有留下”的情况。[C9]

**第六，部分学习规则仍受旧层级影响。** 复习接口按 `node_level == 2` 选择内容和计算总数。当前教师课程按讲组织，读取时又转换为学习界面使用的结构。现有转换可能使部分课程仍可用，但不能因此推定所有新课、导入课、空讲和多小节课程都正确。学习范围判断应共用一处明确规则。[C6]

**第七，存在重复入口与职责交叉的整理任务。** 同步 Markdown 导入直接解析并保存，持久导入则通过任务处理；两者都在当前应用中注册。是否保留兼容入口可以根据调用者决定，但校验、归属、正式写入和错误处理应共用。任务管理、课程仓储、教师内容读取与存储之间的循环依赖，也应在这次共有能力整理中处理。[C2、C12]

### 4.3 本次没有证明的事项

本次未启动应用、未调用真实模型、未操作生产课程、未运行完整学生流程，未重新执行全部测试。现有测试文件能够提供后续回归入口，但“测试存在”不等于“本轮测试通过”。源码中的失败恢复、并发控制和权限检查均需在对应实际场景中验证。

因此，当前结论是“大部分能力有可复用基础，几个跨模块关系与结构问题已被定位”。目前不能给出完成百分比，也不能承诺恢复界面后即可直接面向所有学生上线。

## 五、内容设计：共同课程与各自记录怎样组成产品

### 5.1 产品全景

```text
教师要求／学生学习目的 + 已有资料 + 学科与内容要求
                         ↓
                     课程设计
                         ↓
                课程结构与完整课程内容
                  ↙                ↘
        教师备课与教学文件          学生学习与配套服务
       教案、大纲、日历、评分       阅读、笔记、练习、错题
       讲义、题库、演示课件         AI 辅导、进度与复习
                  ↘                ↙
             教学反馈与各自有权使用的学习事实
                         ↓
               判断问题、提出修改建议
                         ↓
              有权用户决定、执行并保留结果
                         ↓
                 后续教学与学习验证
```

这张图表达共同关系，不表示教师自动拥有学生全部笔记和会话。教学反馈、学生个人记录和可供教师查看的汇总信息，需要分别确定权限。第一版不因建设学生端而自动扩展班级管理、选课系统或公共课程广场。

### 5.2 需要固定的对象与保存责任

| 对象 | 保存的内容 | 正式保存责任与关系 |
| --- | --- | --- |
| 课程 | 稳定身份、所有者、名称、学习范围和基本信息 | 课程仓储；进入备课或学习不改变课程身份 |
| 课程设计依据 | 目标、起点、资料、要求和必要约束 | 与课程和本次生成绑定；生成后修改输入不悄悄改变已执行任务 |
| 原始资料 | 上传原件、解析结果、用途和引用位置 | 资料仓储；原件与生成正文分开，多个用途引用同一原件 |
| 课程正文 | 完整知识内容、顺序、稳定内容标识与修订 | 同一门课程的同一正文只有一个正式保存者；阅读、导出和预览读取它 |
| 教案与教学文件 | 教学安排、学校要求、评分规则、日历等 | 各自仓储保存其专有字段，引用课程与来源修订，不各存一份课程正文 |
| 题目 | 题面、作答要求、评分依据、答案和修订 | 正式题库；学生作答绑定具体题目修订 |
| 学习记录 | 笔记、批注及其原文位置、状态和修订 | 学习记录仓储；按用户与课程保存 |
| 作答记录 | 草稿、提交内容、评分、提示使用、再练关系 | 作答仓储；错题本从这些记录读取，不另造错误历史 |
| 学习事件与位置 | 实际发生的行为、当前阅读位置和继续状态 | 各自记录明确事实，避免重复写入同一事件 |
| 学习者模型 | 根据同批事实得到的学习情况解释 | 可重新计算；不能反向替代原始作答和记录 |
| 修改方案与回执 | 修改理由、范围、基线、用户决定、实际结果 | 复用现有课程修改能力，记录成功、失败、未变更和撤销结果 |
| 生成任务 | 输入、归属、阶段、检查点和执行结果 | 现有任务系统；页面只展示和发出允许的操作 |

其中必须特别区分三组关系。

**课程目录与教学大纲。** 学生需要课程范围和内容顺序，学校要求提交的教学大纲则包含目标、学时、考核等正式要求。两者可以共享字段和来源，但不能要求学生填写所有行政字段才能生成学习内容。

**课程正文与教学表达。** 教师课程的讲义已经被定义为师生共用的完整材料。PPT、导出文档和学习页面可以采用不同表达形式，但需要对应同一来源。第一版不恢复旧“教师保存后再写一份学生正文”的双写方式。[P2、C7]

**课程内容与个人学习记录。** 教师修改讲义，不能覆盖学生笔记和作答；学生要求换一种解释，不能默认改动所有人使用的课程。个人补充、临时回答与正式课程修改需要可区分。

### 5.3 课程正文统一到什么程度

当前教师正文由教师课程仓储保存，再转换为阅读所需的 `CourseDocument`；历史学生课程和导入课程具有既有读取方式。本报告建议以“同一内容只有一个保存责任方、上层通过稳定接口读取”为统一目标，而不把第一步变成搬迁所有历史数据。

新建学生课程应复用同一套课程规划与正文生产能力。其正式正文保存方式，需要与教师生成链一起固定：可以继续使用现有分讲正文仓储，由共有服务承担调用；不能因仓储名称带有 teacher，就复制出一套 learner 仓储和写入逻辑。是否调整内部命名，以职责是否清楚、迁移是否安全为依据。

历史导入课程如果继续由课程文档仓储保存，应作为明确的内容来源，由统一读取接口处理。不同来源的数据格式并存不必然违反唯一性；同一课程正文存在两个可独立写入、互不对账的保存者，才是必须消除的问题。

## 六、逻辑设计：必须联合补齐的六组关系

### 6.1 课程创建、生成与首次使用

完整过程应从使用目的和资料开始，形成课程结构与内容，最后进入可用的备课或学习现场。教师可以检查教案和配套文件，学生主要处理学习范围与课程内容。两边复用资料理解、教学规划、正文生成和题目能力，但界面不要求出现相同步骤。

当前讲义生成依赖教案中的教学安排与内容结构。学生模式不能简单跳过这一步，也不能不加判断地把完整教师流程藏到后台。建议先从既有合同中分清：哪些字段直接保证正文的目标、顺序、例题和练习质量，哪些字段只服务教师授课和学校文件。前者保留为共同生成依据，后者按教学用途生成。该调整需要用相同资料的单讲样本比较内容完整性、等待时间、模型调用与人工修改量，再决定具体简化范围。

一键生成应把已经明确的操作连续执行，同时保存逐项状态。资料不足时只要求补充影响结果的内容；已有资料可以直接阅读的，不强制整套重生成。部分讲次完成后，应明确哪些可以阅读、哪些还在生成。失败不清空成功内容，继续执行不重复生成已经完成的部分。

**这一组必须同时调整：** 创建表单、输入对象、生成服务、任务类型与恢复、正文保存、首次阅读入口。完成条件是教师原流程保持可用，学生也能独立得到与自己要求一致的课程。

### 6.2 来源、版本与课程变化

课程资料、正文、题目、配套文件和学习记录需要知道自己依据的内容版本。单个稳定内容标识解决“指向哪一段”，修订标识解决“依据哪一次内容”。只有两者一起保存，正文变化后才能判断原笔记、旧题目和历史作答是否仍然适用。

例如教师修改某讲公式：未改变的段落与笔记继续保留；引用该公式的题目和文件标明需要检查；学生以前的作答继续对应当时题目，不按新答案改写历史成绩。原段落已被删除或含义发生较大变化的笔记，应保留原引用并说明位置变化，不能悄悄挂到另一段正文上。

同时需要决定正式学生读取哪一份可用内容。当前教师预览读取教师当前正文，并在来源变化时要求刷新；正式学习可能跨越多天，不能照搬临时预览的全部规则。建议为一次学习保存所用修订，内容更新时提示影响并保护当前作答与笔记。具体采用最新可用修订还是保留此前学习版本，见第十一章。这里不要求恢复已经删除的教师发布步骤。

**这一组必须同时调整：** 来源记录、内容标识、读取接口、题目修订、笔记定位、课程修改与版本变化提示。完成条件是“一处变化能够解释影响，同时明确保留不受影响的内容”。

### 6.3 阅读、笔记、AI 与练习

学习页面中的这些能力需要共同理解当前课程、讲次、小节和引用位置。学生选中文字提问后再滚动，已经发送的问题仍对应原引用；从正文进入练习，题目与当前范围相符；关闭练习或笔记详情，可以回到原来的位置。

前端可以保存暂时展开状态、输入草稿和滚动位置，但正式笔记、作答和学习进度仍由后端保存。刷新后通过正式接口恢复；慢请求返回时不能覆盖用户刚写的新内容；保存失败时保留输入并说明怎样继续。当前笔记侧栏与行内编辑修复应作为回归基线。

**这一组必须同时调整：** 页面上下文、Store、正文定位、学习记录、AI 输入、练习入口与保存反馈。完成条件是工具之间可以连续使用，位置与记录不混乱。

### 6.4 练习、错题、再练与学习判断

练习使用正式题目，学生每次提交形成独立作答；错题本从作答结果中找出仍需要理解和巩固的内容，再练记录与原作答关联。再次做对可以改变当前复习建议，但不删除第一次错误，也不自动证明长期掌握。

判断学习情况时要保留证据区别：读过正文、看过解析、使用提示后答对、独立答对新题，是不同事实。界面可给出清楚建议，后端应保留形成建议的依据。没有足够证据时说明待继续验证，不制造看似精确的掌握百分比。

复习范围要按真实可学习内容确定，不能让目录层级数字在不同模块中各自决定。错题本、学习概况与 AI 辅导消费同一批正式事实，不各写一份学习画像。

**这一组必须同时调整：** 题目可用性、作答合同、评分、错题筛选、再次练习、复习范围与学习者模型。完成条件是一个学生的同一次作答在不同功能中具有一致含义。

### 6.5 教学文件与共同课程信息

教师端保持当前备课工作台，配套文件继续归入课程文件。教学大纲、教学日历和评分标准共享相关课程信息，但各自有明确用途。一次填写学时与考核安排后，其他文件应引用或生成对应内容，避免重复录入后互相矛盾。

已有评分细则与自查清单采用模板、输入校验和确定性导出。确定性的字段汇总、课时计算、文件格式不需要额外调用模型；只有需要理解材料或补充内容的部分使用 AI。不能把“一键生成各种文件”扩成每份文件都重新理解整门课程的独立链路。

教师手工修改的字段应有保存与保护机制。上游信息改变后，展示实际受影响项，再由教师决定更新；生成失败时旧文件继续保留。导出文件对应当时的来源与修订，不能在后台悄悄变化。

**这一组必须同时调整：** 共有字段、文件模板、生成输入、手工保存、影响说明、批量任务与导出。完成条件是文件能够实际提交和使用，内容相互一致。

### 6.6 身份、权限、任务与失败恢复

身份回答“当前是谁”，角色与权限回答“能够做什么”，课程归属回答“谁拥有这门课”，学习记录归属回答“这次行为属于谁”。同一个人进入学习界面不应因此变成另一个正式账号；同时，教师身份不能成为读取其他人私人笔记的默认许可。

任务操作使用准确的任务身份。暂停、继续、取消、重试只作用于当前有权操作的任务；页面关闭与重新打开只是离开和恢复现场。模型请求已完成但保存失败时，应进入保存或对账恢复，避免重新调用模型覆盖已有结果。

各类任务允许不同恢复方式。当前讲义链保留中断片段，由用户主动继续，不能为了“统一任务”恢复成一律自动重跑。统一的是任务归属、状态表达、执行记录和恢复入口，具体恢复条件由该任务的业务规则决定。

**这一组贯穿前五组：** 账号接入、课程访问、个人数据、HTTP/SSE/WebSocket、后台任务与存储。它是所有联合开发的共同要求，不能安排到界面完成之后再补。

## 七、交互设计：保留教师端，恢复学生学习的完整顺序

### 7.1 共同入口与两种工作方式

建议以“我的课程”作为共同的课程管理概念，按用户任务进入备课或学习。教师原有的“我的课程／我的日历”、备课工作台和课程文件继续保留；学生入口提供新建、导入和继续学习。具体是同一首页中的切换，还是共享导航下的两个首页，应在桌面结构稿中比较，不因共用后端强迫两个首页相同。

同一人能够使用哪些工作方式由账号与授权决定，工作方式切换不改变正式身份。暂不承诺普通学生自动拥有教师专用文件和所有课程管理权限。

### 7.2 页面职责

| 页面或区域 | 主要任务 | 应有内容与操作 | 需要避免的混合 |
| --- | --- | --- | --- |
| 课程入口 | 找到课程并开始工作 | 新建、导入、搜索、继续、真实生成状态 | 学生进入后默认落到教学日历 |
| 教师备课工作台 | 准备和修改教学内容 | 保留大纲、教案、讲义、PPT 与任务信息 | 为接入学生端重做已有备课流程 |
| 课程文件 | 查看、整理和导出课程相关文件 | 正式文件、原始资料、配套文件、来源与状态 | 文件列表成为第二份课程数据 |
| 学生学习现场 | 阅读、理解与运用 | 目录、连续正文、笔记／AI、练习与继续位置 | 要求学生逐项处理教师生产阶段 |
| 笔记本 | 集中整理学习记录 | 搜索、分类、排序、编辑、导出、返回原文 | 复制一套与阅读侧栏不同的笔记 |
| 错题本 | 理解错误并再次练习 | 原题、原作答、反馈、个人记录、再练入口 | 只显示错误数量，无法回到题目和正文 |
| 学习概况 | 帮助安排接下来的学习 | 进度、待继续任务、复习建议与依据 | 将阅读次数直接展示成掌握结论 |

第一版先保证课程内的笔记与错题完整可用。是否立即提供跨课程汇总属于范围选择；如果需要，扩展查询能力和定位关系，不新建第二套记录。

### 7.3 应继承的具体交互

学生学习现场采用现有文档已经明确的结构：左侧目录，中间连续正文，右侧笔记或 AI 助手，底部提供学习工具。右栏切换不丢会话和笔记草稿，练习提问时题目仍可见，长内容自然换行，主要操作靠近所影响的内容。[交互与界面设计](../../交互与界面设计.md)

教师端继续使用现有蓝紫色体系、组件与布局；学生端也复用相同设计变量，但按学习任务安排信息密度。界面统一体现在相同对象、动作与状态具有一致表达，不要求所有页面都套同一种外壳。

知识图谱不进入新学生主导航和验收范围。已有知识关系在内部确实被课程、题目或上下文使用时保留明确依赖，不以“暂不做界面”为由直接删除底层代码，也不把知识图谱维护作为学生学习的前置步骤。

### 7.4 每个功能都要回答的交互问题

用户从哪里进入，正在处理哪门课和哪份内容，有哪些可用操作，操作后发生什么，已经保存了什么，失败后如何继续，以及如何返回原位置。这组问题来自现有项目规则，也应成为页面设计与验收的共同依据。

错误与任务状态在对应位置表达：生成失败不覆盖已有正文，后台读取失败不反复弹窗打断阅读，未完成保存不显示已保存。教师预览与正式学习可以共用组件，但必须让数据是否保存的行为清楚、可验证。

## 八、技术设计：怎样做到唯一、可用、干净、稳定

### 8.1 共有能力与职责

建议在现有应用内整理职责，暂不引入新的服务部署或复制应用。

```text
教师界面／学生界面
        ↓
身份与权限、参数与返回结果
        ↓
课程生成与使用、教学文件、学习记录、练习与 AI 协作
        ↓
各自的业务规则与正式修改命令
        ↓
各自仓储 + 任务、检查点与执行回执
        ↓
存储、模型调用、文件解析与导出
```

页面负责组织任务；接口负责接入与调用；业务服务负责过程与规则；仓储负责自己的数据保存；基础能力不反过来决定教师或学生流程。同一项能力可被多个入口调用，但不能因此产生不同的保存规则、评分规则或恢复规则。

### 8.2 “链路唯一”的具体检查方法

每项核心操作应能写出一条从入口到结果的关系，并回答下面的问题。

| 检查项 | 合格标准 |
| --- | --- |
| 正式数据 | 明确由哪个仓储保存；缓存、导出、页面状态都不能独立成为正文或记录 |
| 业务规则 | 手工操作、AI 操作、批量操作、重试与兼容入口复用相应底层规则 |
| 写入路径 | 权限、修订、允许动作与重复提交检查作用于所有入口 |
| 任务状态 | 前端、后台与恢复使用同一任务身份和持久状态 |
| 学习事实 | 笔记本、错题本、学习概况与 AI 读取可对账的事实，不各写一份解释性历史 |
| 修改结果 | 回执反映实际成功、失败和未变化；不能把预计影响当作已修改结果 |
| 兼容边界 | 说明保留的读取者、调用者、允许操作与退出条件 |

“唯一”不要求每项能力只剩一个 HTTP 地址，也不要求所有内容放进一张表。多个入口可以指向同一个服务，不同对象也应有独立责任。需要消除的是重复业务实现、绕过正式写入的旁路，以及同一事实的多个独立维护者。

### 8.3 本次依赖检查及其含义

运行项目现有 `scripts/audit_backend_dependencies.py`，标准检查返回失败。进一步调用同一脚本的统计函数，结果如下：

| 核查项 | 当前结果 |
| --- | --- |
| 生产 Python 模块 | 333 个 |
| 循环依赖组 | 1 组，12 个模块 |
| 其他现有架构规则违规 | 该脚本计算结果为 0 |
| `jobs.manager` | 10,874 行，直接依赖 62 个生产模块 |
| `course_generation.service` | 9,988 行，直接依赖 44 个生产模块 |
| `routers.teacher_lesson_authoring` | 6,681 行，直接依赖 41 个生产模块 |

循环组中的实际依赖包括：

```text
storage → course_repository → learning_progress → learning_events → storage

course_repository → teacher_content_projection → dependencies → course_repository

teacher_lesson_authoring → teacher_script → canonical_content_repair
          ↑                                      ↓
teacher_content_projection ← course_repository ← course_commands
```

以上箭头来自静态导入关系；检查也统计函数内部的延迟导入，因此不能直接推导运行时一定会出现循环导入错误。它证明模块责任已经相互牵连，需要用清楚的依赖方向降低修改影响。完整模块与实际边列表保存在[后端依赖核查](./后端依赖核查.json)中。

从具体代码看，有三处可以形成有限、明确的整理任务：

1. `storage` 为抛出 `CourseDocumentConflict` 反向引用课程仓储。可把共同异常放入更基础的模块，保持上层兼容导入，避免存储层为了一个异常依赖业务仓储。
2. `teacher_script` 只需要公式显示修复，但所引用的 `canonical_content_repair` 同时依赖课程命令和仓储。可分离纯文本修复与正式内容修复动作，使讲义格式处理不把整条写入链带进来。
3. 教师内容转换通过 `dependencies` 获取仓储，而 `dependencies` 本身又组装课程与教师仓储。可由上层明确传入已加载内容或仓储，让内容转换保持读取与转换职责，减少双向查找。

这些建议直接来自当前依赖，仍需逐项检查调用者并做回归。不能为了让检查通过而排除模块、忽略延迟导入或放宽规则。课程仓储同时承担内容读取和学习目标转换的部分，也要确认哪些应由读取协调层负责。

### 8.4 怎样整理大文件

任务管理器应集中管理任务身份、状态、检查点与恢复登记；课程规划、正文生成和题目处理等业务过程由对应服务承担。课程生成服务应负责共有生成过程，教学定义与内容规则继续由现有 `teaching_design` 等模块提供。路由中的复杂业务决策，应进入可以被多个入口复用的服务。

拆分以真实职责与调用关系为依据。仅把一个大文件切成若干文件、仍然互相调用，不能证明结构改善。反过来，当前 PPT 模块较大也不意味着本轮必须整体重做；除非它影响师生共有正文、配套文件或任务关系，否则维持已有边界。

### 8.5 旧链路怎样退场

先按能力列出所有入口、调用者、读写对象和恢复路径，再作判断：同样功能由新链完整承接的，旧入口改为明确适配或退出；仍保存历史数据的，保留必要读取；仍有独特能力的，先迁入正式责任模块再删除外壳。

同步导入、旧课程生成、旧章节处理、前端预览分支与历史题目适配分别检查，不能因为名称带有 legacy 就直接删除。也不能因为旧函数仍被调用就永久保留独立实现。删除完成必须同时证明：当前入口不再依赖它，历史数据仍能按约定读取，失败恢复没有引用被删状态。

数据整理前建立仓库外、带时间戳的可恢复备份。已退役内容是否实际迁移或清理，使用独立记录说明，不把代码删除等同于数据处理完成。

## 九、联合开发安排

### 9.1 先形成一套共同设计

开发开始前，需要形成足以指导实施的内容、逻辑、交互和技术说明，重点固定第六章中的关系。文档要明确对象、条件、变化、操作与验收，不以篇幅作为严格程度的证明。

本报告中的建议经确认后，写回已有正式位置：教学对象进入《教学内容设计》，运行机制进入《产品逻辑设计》，页面职责进入《交互与界面设计》，代码责任进入《系统架构》，实际完成状态进入《产品状态》。报告保留分析依据，不发展成第二套需要长期同步的产品正文；项目 AGENTS.md 仍由用户维护。

相关 OpenSpec 已覆盖教师课程工作区、分讲生产、学习记录、课程修改和任务恢复。实施前应明确哪些现有合同继续生效、哪些需要修改、哪些旧任务被新范围承接，避免多个 change 同时声称拥有同一生成或学习流程。

### 9.2 开发按完整结果组织

| 工作安排 | 必须一起改的内容 | 本阶段交付 | 进入下一阶段的依据 |
| --- | --- | --- | --- |
| 1. 固定共同设计与基线 | 对象归属、教师／学生入口、内容来源、版本规则、功能范围、现有合同 | 可对照代码的设计、保留／调整／退出清单、固定测试样本 | 六组关系没有互相矛盾的定义；未确定项明确影响范围 |
| 2. 统一内容访问与正式写入责任 | 身份、课程访问、正文来源、个人记录归属、复习范围、循环依赖中的基础责任 | 共用访问与写入规则、稳定读取接口、结构整理和回归结果 | 教师原路径保持可用；学生使用所需的权限与保存边界可验证 |
| 3. 联合完成课程生成与学习使用 | 学生创建与导入、共有生成服务、任务恢复、正文阅读、笔记、练习、错题和 AI 上下文 | 可以连续使用的学生工作区；共用课程能力；可保存和恢复的正式记录 | 从新建或导入到再次回来学习全部贯通，当前教师流程没有回归 |
| 4. 完成课程变化与教学文件联动 | 修改影响、题目修订、笔记定位、学习版本、配套文件生成与导出 | 变化前后可对照、未受影响内容保留、失败可继续的完整结果 | 正文与配套文件一致，学生历史记录不被新修订改写 |
| 5. 收束旧入口并做发布验收 | 兼容调用、旧写入、静态依赖、跨用户与故障回归、部署与恢复 | 单一正式实现、必要兼容范围、发布与恢复证据 | 本轮功能共同达到第十章标准 |

这张表表示主要依赖与共同完成条件，不表示第二阶段才设计权限，或第四阶段才考虑版本。所有阶段从第一阶段就遵守相同关系；后续阶段完善实现与验证。结构整理应围绕这些关系进行，避免先花很长时间重写全部后端，也避免把基础责任问题留到页面上线之后。

每组工作应有一个对完整结果负责的人或开发任务，前端、后端和验收围绕同一输入与结果协作。不能把“前端完成”“接口完成”“模型返回”分别当作该组工作已经交付。

### 9.3 第一版范围建议

本轮共同完成：保留教师备课与课程文件，提供学生新建或导入、课程阅读、笔记、练习、错题再练、AI 辅导、进度与继续学习，并处理这些能力需要的身份、版本、保存、联动和恢复。

暂缓：知识图谱产品化、跨课程的复杂自适应规划、完整班级与选课管理、开放课程广场、移动端适配。跨课程笔记与错题汇总可在课程内流程完成后扩展。以上暂缓项中，知识图谱由本次讨论明确；其余是范围建议，应在第一阶段确认，不能当作已经获准删除的能力。

“一键生成”先覆盖当前明确、已有模板与输入来源的文件。学校任意模板自动理解、任意复杂文档无损生成不作为未经验收的承诺。已有模板之外的新文件类型应有实际样本和明确字段，再纳入计划。

## 十、怎样判断开发真正完成

### 10.1 完整使用场景

验收使用隔离环境和明确的测试数据，不修改正在使用的真实课程。至少包括下列场景，教师与学生都使用正式入口：

| 场景 | 必须看到的结果 |
| --- | --- |
| 教师创建并备课 | 现有大纲、教案、讲义、课程文件与 PPT 流程保持可用，配套文件状态真实 |
| 学生从主题和资料创建课程 | 不填写教师专用行政字段也能完成；正文与范围一致，任务归本人，失败可继续 |
| 学生导入已有课程 | 归属明确，原文与目录可读，公式与图表失败有真实提示，不重复创建课程 |
| 同一段内容连续阅读、记笔记、提问、练习 | 引用与上下文正确，切换与刷新不丢记录，返回原位置 |
| 错题与再次练习 | 原作答保留，再练能够关联，错题本与学习概况读取一致结果 |
| 教师修改学生已阅读的内容 | 未变化内容保留，受影响项可辨认，个人笔记与已提交作答不被覆盖 |
| 教师预览与正式学生使用 | 预览不产生正式学习记录；正式使用能够持久保存，二者互不混入 |
| 两个用户使用同一课程 | 课程权限符合约定，个人笔记、作答与会话互不串用 |
| 重复提交、断流、刷新、部分失败 | 无重复正式结果；已成功内容保留；按原任务恢复，返回真实状态 |
| 来源改变与保存冲突 | 不静默覆盖，保留本地输入或最后可用结果，说明下一步怎样处理 |

### 10.2 “唯一、可用、干净、稳定”的验收含义

**唯一：** 核心操作的入口、服务、仓储与恢复路径能够逐项追踪。手工、AI、批量与重试共用规则；同一正文、记录和任务没有两个独立正式保存者。兼容入口列明调用者与退出条件。

**可用：** 用户能从正式入口完成预期任务，看到过程、使用结果、修改内容并处理失败。只有接口返回成功、只有页面外壳、只有一次演示均不能作为完成证据。

**干净：** 当前发现的循环依赖消除且现有检查不降级；已确认退役的入口和写入退出；文件与模块职责清楚；无已知且未解释的重复业务实现。静态检查通过仍需结合调用关系审查，不能只凭一个指标宣布全库干净。

**稳定：** 重复请求、并发保存、断网刷新、来源变化、部分失败、模型不可用和恢复执行均有确定结果。用户已经完成的工作不会因新尝试失败而消失，错误状态与实际保存结果一致。

### 10.3 生成质量与实际效率

用相同课程资料和目标比较调整前后的生成结果，分别记录：资料准备时间、首次可读内容时间、完整交付时间、模型调用次数、失败与恢复次数、必要内容覆盖、事实与公式错误、用户修改量。课程长度与学科不同的样本分开记录，不用短请求速度代替整课效率。

保留至少一类数学推导较多的课程、一类概念与案例较多的课程，以及一份已有资料导入样本。选择这些样本是为了暴露不同问题，不代表三份样本就证明覆盖所有学科。合格阈值应在固定样本和基线测量后确定，不在没有证据时给出统一成功率或秒数。

对每项新增模型调用，应能说明它解决哪个已观察问题，并比较是否减少实际返工。能用确定性规则完成的计算、模板填充与格式修复优先由代码承担；需要理解、解释和生成的部分使用现有模型能力。

### 10.4 验收证据分开保存

针对性测试、完整回归、静态结构检查、真实模型样本、中文桌面操作、生产激活与恢复分别记录。某一项通过不能代替其他项。文档更新写明当前实际状态，不沿用旧日期和旧测试数量证明本轮完成。

现有测试可以从学习记录、学习运行态、学习继续、作答与针对再练、教师预览、统一教师内容、生成任务持久化和身份接入等文件开始扩展。只新增能够验证业务关系和失败行为的测试，避免为展示测试数量而逐行复制实现。

## 十一、实施前需要确定的具体选择

以下问题不阻碍本报告形成判断，但会决定正式合同与开发范围。建议在第一阶段集中确定，避免每个模块各自作答。

| 选择 | 建议 | 影响 |
| --- | --- | --- |
| 第一版学生主要使用自己创建的课程，还是同时学习教师提供的课程 | 先保证自建／导入完整可用；教师课程访问方式同时设计，若本轮提供则纳入完整验收 | 决定课程列表、授权与学习版本范围，不等于必须建设完整选课系统 |
| 同一个账号怎样进入备课与学习 | 同一正式身份，按有权使用的工作方式显示入口 | 影响账号接入、首页与权限；不能靠前端切换伪造教师角色 |
| 新学生课程怎样复用教师生成能力 | 共用规划、正文与题目能力；分清正文所需教学结构和教师专用文件 | 决定生成请求、内部步骤、保存者和实际等待时间 |
| 学生读取教师课程的哪个版本 | 读取明确可用的内容，并记录当前学习所用修订；更新时保护已有作答与笔记 | 需要检查现有修订留存与恢复能力，不能只在前端保存一个版本号 |
| 学生怎样修改自己学习的内容 | 自有课程通过正式命令修改；他人课程中的补充先作为个人内容或建议 | 影响 AI 动作授权、来源关系和课程修改回执 |
| 跨课程笔记、错题与复习汇总是否首版必需 | 先完成课程内关系，聚合功能按实际使用需求扩展 | 影响查询和性能，不应改变正式记录归属 |
| 教学配套文件支持到什么范围 | 先覆盖已有模板和能提供真实样本的文件 | 避免“一键生成”被理解为已支持任意学校模板 |

这些选择确定后，再形成可实施的字段、接口与状态约定。后续运行结果若表明设计不合理，回到相应的内容、逻辑或交互层修改；不能用底层临时字段长期掩盖上层问题。

### 12.2 核查范围与复现

在灵知应用目录中复现标准检查：

```bash
./.venv/bin/python scripts/audit_backend_dependencies.py --report --limit 8
```

当前标准检查因循环依赖返回 1，尚未执行后续报告输出；随附 JSON 的规模统计通过调用同一脚本的静态分析函数取得，其他架构规则单独计算。它不代表标准检查通过。报告列出的循环箭头取自实际依赖边，标准错误输出中的模块排列仅表示同一循环组，不应当被当作逐边调用顺序。
