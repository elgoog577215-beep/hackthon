# 并发容量标定运行手册（B-4）

> **这份手册解决一件事**：正文并行阶段的并发默认值 `8` 是**按当前端点实测定的**，
> **换端点或换模型必须重测**。照着下面的步骤跑一遍，20~40 分钟就能重新定这个值。
>
> 当前标定：自部署千问 `qwen3.6-35b-a3b` @ `221.12.22.187:30938`，2026-08-17。

## 一、为什么必须重测，不能沿用

并发的最优值不是代码属性，是**端点属性**。它同时取决于：

* 端点的实例数 / 批处理配置（vLLM 的 `max_num_seqs` 之类）；
* 模型大小与单条流的生成速度；
* 你这个账号的配额与限流策略（免费额度尤其敏感）。

同一份代码换到别的端点，最优并发可能是 2，也可能是 32。
**沿用别人的数字比不调还糟**——调高了每条流都变慢，调低了白白排队。

## 二、怎么重测（三步）

### 第 1 步：确认端点通

```bash
curl -s -X POST "$AI_API_BASE/chat/completions" \
  -H "Content-Type: application/json" -H "Authorization: Bearer $AI_API_KEY" \
  -d '{"model":"'"$AI_MODEL"'","messages":[{"role":"user","content":"hi"}],"max_tokens":10}'
```

顺带看一眼返回里有没有 `usage` 字段——有的话账单能拿到 **provider 真实 token 数**
而不是本地估算，标定会更准（见 `backend/generation_telemetry.py`）。

### 第 2 步：跑并发扫描

```bash
cd <repo>
python3 backend/tools/content_parallel_bench.py --limits 2,4,6,8,12,16
```

这个脚本走的是**真实正文生成路径**（`CourseService.generate_node_content_stream`，
流式），不是自己拼的 prompt——所以排队、重试、心跳都算在内。
它不依赖教案语义门，可以单独跑。

> 还有一个 `content_phase_bench.py` 是**非流式**的同形状基准，跑得快，
> 适合快速摸个大概；但**定默认值要以流式那个为准**，
> 因为两者结论会不一样（见下面"教训"一节）。

### 第 3 步：多跑几轮，别信单次

```bash
for r in 1 2 3; do
  python3 backend/tools/content_parallel_bench.py --limits 4,6,8 \
    --telemetry-dir /tmp/cal/r$r
done
```

**单次结果不可信**：本次标定中同一个并发档的墙钟范围能到
52.6s~89.0s（相差 69%）。至少 3 轮，看均值和中位，不看单点。

## 三、判断标准：看三个数，找拐点

每个并发档看这三个数：

| 指标 | 含义 | 怎么读 |
| --- | --- | --- |
| **墙钟** | 这一阶段总耗时 | 越低越好，但要看多轮均值 |
| **排队时长** | 请求在容量队列里等了多久 | **接近 0 = 队列没在限流**；很大 = 并发设小了 |
| **有效并行度** | 在飞时长合计 ÷ 墙钟 | 逼近并发上限 = 真的并起来了 |

### 拐点长什么样

**并发不足**（该往上调）：
* 排队时长很大（本次标定：并发 2 时排队 274.6s）
* 有效并行度 ≈ 并发上限（说明位子一直是满的，是上限卡着）
* 墙钟随并发上调明显下降

**已经到位**（就用这个值）：
* 排队时长掉到接近 0
* 墙钟不再随并发上调而下降
* **单节耗时开始变长** ← **最重要的信号，别漏看**

**过头了**（该往回调）：
* 单节耗时明显变长，但墙钟不再改善
* 说明端点在把并发请求**摊薄**：每条流都变慢，总吞吐没涨
* 本次标定：并发 4→8，单节中位从 35.2s 涨到 44.4s（+26%），
  而墙钟只从 82.0s 到 65.5s，**收益全被单节变慢吃掉一部分**

> **判据一句话**：**排队掉到 0 之后，再往上调只会让单节变慢，不会让整体更快。**
> 拐点就在"排队刚好归零"的那一档附近。

## 四、本次标定结果（当前端点）

8 个小节的正文阶段，走真实流式路径，多轮：

| 并发 | 墙钟均值 | 墙钟范围 | 排队 | 有效并行度 | 单节中位 |
| ---: | ---: | --- | ---: | ---: | ---: |
| 2 | 151.6s | — | 0.0s | 1.80 | 35.0s |
| 4 | 82.0s | 78.9~85.9s | 0.3s | 3.51 | 35.2s |
| 6 | 66.4s | 52.6~89.0s | 0.8s | 4.68 | 33.9s |
| **8** | **65.5s** | 56.4~75.1s | 2.7s | 5.63 | 44.4s |
| 12 | 54.2s | 单次 | 2.7s | 6.48 | 45.5s |

**结论**：
* **4 → 8：墙钟 −20.1%**（82.0s → 65.5s），有效并行度 3.51 → 5.63。这条是实的。
* **6 与 8 分不出高下**（均值差 1.0s，区间高度重叠）。默认取 8 是保守选择，
  取 6 同样合理；**不要声称 8 明显优于 6**。
* 12 只测了一轮，且单节已明显变长，不建议。

**默认值 `COURSE_CONTENT_CONCURRENCY=8`** 就是这么来的。

### ⚠️ 这份标定与任务书 14 分 35 秒基线的差距

本标定里单节中位 **27~46 秒**，而真实基线的单节中位是 **4 分 11 秒**——
**相差约 7 倍**。原因是这个基准用的是精简教案，产出约 5 千字/节，
真实小节的上下文与产出都大得多（试过 `--words 3000` 拉长，
输出仍受 prompt 与 token 预算约束，拉不到真实量级）。

**所以下面这条是推算，不是实测**：
按同比例（-20.1%）折算，14 分 35 秒 → **约 11.6 分钟**。

真实小节更长意味着"端点摊薄效应"可能更明显（每条流更慢），
也可能因为单节本身够长而让排队占比更小——**两个方向都有可能，我没有实测**。
**要拿真实数字，必须等教案语义门修好后跑一次完整课程**，
用 `backend/tools/generation_bill.py` 看正文阶段那一段。

## 五、改哪里

标定出新值后，**三处一起改**（少改一处会留下不一致的兜底把新值盖掉）：

| 位置 | 说明 |
| --- | --- |
| `backend/course_generation_budget.py` | dataclass 字段 + `from_env` 兜底，两个都要改 |
| `backend/task_manager.py` 的 `DEFAULT_MAX_CONCURRENCY` | 没传预算时的兜底 |
| `.env.example` | 写死的值会把新默认盖掉 |

**但日常不需要改代码**——环境变量随时覆盖：

```bash
COURSE_CONTENT_CONCURRENCY=2    # 免费额度 / 端点变弱，立刻降
COURSE_CONTENT_CONCURRENCY=16   # 端点更强，往上调（硬上限 16）
```

另有 provider 侧队列参数（`backend/ai_capacity.py`）：
`AI_PROVIDER_INITIAL_CONCURRENCY` / `AI_PROVIDER_MAX_CONCURRENCY`。
容量控制器带**慢启动**：没见过失败前每成功一次放宽一位，
首次失败即退回保守 AIMD。所以 `INITIAL` 不必设很高，它会自己爬上去；
但**冷启动那一波受 `INITIAL` 约束**，短脉冲阶段可以把它直接设到标定值。

## 六、两个并发数不是一回事，别混用

仓库里有**两套**并发标定，测的是不同的东西，结论也不同。混用会调错参数：

| | `scripts/qwen_concurrency_ramp.py` | 本手册（`content_parallel_bench.py`） |
| --- | --- | --- |
| 测什么 | **端点的原始吞吐容量** | **正文阶段这 8 个小节的墙钟** |
| 负载 | 尽量压满，找 tok/s 饱和点 | 就 8 个单元，跟真实阶段一样 |
| 结论 | 约 1840 tok/s 饱和，膝点 24 | 4→8 降 20%，6 与 8 打平 |
| 用来定 | `AI_PROVIDER_MAX_CONCURRENCY`（上限 16） | `COURSE_CONTENT_CONCURRENCY`（默认 8） |

**为什么两个数差这么远**：端点能吃下 24 路并发，不代表正文阶段该开 24 路——
**这个阶段总共只有 8 个小节**，开到 24 也只有 8 个在跑。
阶段的并发只需要"够覆盖这一阶段的单元数"，再多是浪费；
而 provider 队列上限要覆盖**全链路同时在飞**的所有请求，所以取更大的值。

一句话：**`AI_PROVIDER_MAX_CONCURRENCY` 看端点能吃多少，
`COURSE_CONTENT_CONCURRENCY` 看这一阶段有多少活。**

## 七、教训：非流式基准会给出错误的最优值

本次标定踩过一个坑，记下来免得重蹈：

我先用**非流式**基准（`content_phase_bench.py`，自己拼 prompt 调 `_call_llm`）
测出"并发 8 明显优于 6，12 相对 8 无收益"，据此定了默认值 8。
后来用**真实流式路径**重测，结论变了：**6 和 8 分不出高下**，
而且并发 8 时单节耗时涨了 26%——这个现象在非流式基准里根本看不出来。

**原因**：流式路径下端点会把并发请求摊薄，每条流的 token 速率下降；
非流式只看总时长，感知不到"每条都变慢了"。

**所以**：快速摸底可以用非流式，**定默认值必须用流式那个**。

## 八、什么时候要重新标定

* 换端点 / 换模型 / 换部署规格（实例数、`max_num_seqs`）
* 从免费额度换到正式通道，或反过来
* 端点侧扩容或缩容
* 观察到排队时长明显变大，或单节耗时无故变长
