# 千问连接故障定位与 SQL 续作阻断

结论：本次确认存在**到已配置千问公开服务端口的间歇性连接故障**。本机 Clash 记录了针对该目标的 TCP 拨号超时，并向客户端返回空正文502。绕开本机代理的诊断请求同样超时。当前还不能确定故障具体位于服务端监听、端口映射、网络路径或访问策略中的哪一处，不能宣称已经修好服务。

用户确认没有千问服务器SSH别名或维护入口。本机仅存在与其他GPU环境有关的SSH配置，没有证据证明其对应此千问服务，因此没有登录无关服务器，也没有重启模型、应用或代理。

## 为什么停止续作

目前无法可靠取得原子化输出。如果继续批量发请求，只会增加失败记录，无法完成对准确性、覆盖、颗粒度和结构的评估。尤其是 `/models` 偶尔可读或一句短回复成功，并不能证明冻结的实际生成请求已恢复。

SQL材料、通用提示词、77项隐藏评测、7节已取得的原始清单和之前所有失败回执继续保留。本次M2请求哈希与冻结请求相同，未加入逐点修改计划、人工答案或反馈。原子化及分类尚未完成，不宣称达到知识树基线。

## 维护方需要检查的具体位置

1. 对照本地推理服务与公开访问入口：分别读取模型列表，并执行一个真实生成请求，确认不是仅发现接口可用。
2. 检查模型HTTP服务的监听与进程状态，以及公开端口映射的在线状态和转发目标。
3. 对照故障时段的TCP连接、代理/映射日志和生成服务日志，确定请求是否到达推理进程；若未到达，先修复连接或映射，不调整课程提示词。
4. 入口恢复后，使用本次冻结的M2原子化请求验证完整流式响应，再补缺失的清单、原子化与全章分类。已有成功清单不人工修改；其类型/引文问题继续作为无指导评测的一部分。

上述为待维护方执行的排查事项，当前未执行服务端操作。没有可用管理入口时，本地无法代替服务端完成修复。
