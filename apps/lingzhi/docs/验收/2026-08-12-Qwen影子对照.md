# Qwen 影子对照评测（2026-08-12）

> 文档状态：一次同 harness、双 provider 的对照实测快照<br>
> **指标口径：预期一致率（expected-agreement）**<br>
> **预期分由 AI 编写、未经教研复核，不等于人工判分一致率**

## 这份对照是什么，不是什么

**是**：把同一批构造任务分别投给两个 provider，看**生成侧**产出率与
**判分侧**是否符合预先声明的判分意图。

**不是**：迁移门禁。按用户 2026-08-12 的口径，本表已**降级为记录**，
用于定位真机冒烟中挂掉的项该怎么修，**不用来决定切不切**。

**也不是**人工判分一致率。清单 H1a/H1b 要求的「判分器与人工判分一致率
> 90%」状态仍为**待教研复核**，不因本表达标而改判。

## 方法

- harness：`scripts/question_form_generation_audit.py`（lz-practice 既有），
  两侧完全相同，未做任何 provider 特化改动。
- 运行位置：临时 worktree `dev/lz-perf-shadow`（基于 lz-practice HEAD
  `2def3ecd`，cherry-pick 适配层 `e3a49bda`）。**未修改任何其他 worker 的
  工作区。**
- 样本：`--per-form 10`，三类题型共请求 30 道。
- 并发：`INITIAL=2 / MAX=4`（两侧一致）。
- **数据红线**：harness 构造一门探针课程（`course_id="form-audit"`），
  全程**不使用真实课程、不使用学生作答**。

## 结论

### 1. 判分侧：两侧都零不一致，且与模型无关

三类题型、两个 provider，预期一致率全部 100%。这符合预期——判分器是
确定性代码，不调用模型。**换 provider 不影响判分侧**，这一条可以沿用。

### 2. 生成侧：Qwen 明显优于 CloudRouter，但**这张表不能证明 Qwen 更强**

CloudRouter 侧 **254 次 JSON 提取失败、95 次截断**，Qwen 侧分别是 **0 和 0**。
两个已知的 CloudRouter 侧缺陷足以解释整个差距：

- `response_format: json_object` 在该端点**不报错也不生效**，模型返回散文
  而非 JSON（用户 2026-08-11 已实测告知）；
- 出题层按 provider 传入的 `max_tokens` 偏小（实测 1536 / 2048 / 4096），
  对更冗长的模型不够。

**所以本表只能说明「在当前配置下，Qwen 侧链路更顺」，不能说明模型能力
排序。** 要做真正的能力对照，需先修掉 CloudRouter 侧的 json_mode 与
max_tokens 问题再重跑——本轮未做，如实记录。

### 3. fill_blank 两侧都差（Qwen 4/10、CR 1/10）

对照 lz-practice 清单里的 DeepSeek 基线（fill_blank 8/10），**两个 provider
都明显退化**。lz-practice 已有归因文档指出该题型的失败集中在**判等口径
覆盖边界**而非模型能力边界。本表的数据与该结论方向一致：
fill_blank 是题型本身的薄弱环节，不是这次迁移引入的。

### 4. 熔断 0 —— 适配层生效

Qwen 侧 127 次调用零熔断。作为对比，**未打适配层时**同一端点会出现
「thinking 吃光预算 → content 为 null → 空响应 → 熔断」的连锁
（已在 2026-08-11 实测复现）。这条验证了 `e3a49bda` 的适配层在真实
出题负载下有效。
