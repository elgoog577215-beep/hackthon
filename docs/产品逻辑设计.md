# 灵知产品逻辑设计

本文定义灵知是什么，以及课程怎样在产品中被创建、生产、使用、调整和验证。教学内容本身由《教学内容设计》负责，用户怎样参与由《交互与界面设计》负责，具体实现由《系统架构》负责，当前完成程度由《产品状态》负责。

本文描述目标产品逻辑。图中出现某项能力，不代表当前代码已经完整实现；现状判断不得写回本图，也不能用当前实现反向缩小正确的产品关系。

## 1. 灵知是什么

### 1.1 灵知处理的核心问题

灵知需要共同解决五个问题：

1. 教师怎样把教学设想转化为完整、专业、可以实施的课程。
2. 大纲、教案、讲义、题目、教学日历、评价标准和演示课件怎样保持同源。
3. 一门持续修改的课程，怎样被明确发布给某个学期、班级和学生使用。
4. 教师教学和学生学习产生的真实证据，怎样分别形成个体补救、班级调整和公共课程改进。
5. 人工智能怎样参与课程设计、内容生产和课程修改，同时保留教师的教学决定权。

### 1.2 核心用户及其真实任务

- **教师**设计课程、准备教学、建立教学实施、开展课堂、检查学习结果并调整课程。
- **学习者**在明确的课程版本中阅读、练习、提问、完成作品、获得帮助并证明掌握。
- **课程设计者**维护课程结构、教学标准、内容模板与可复用课程版本。
- **教务管理者**管理学期、班级、教师、学生、教学场次和课程发布范围。

### 1.3 灵知管理的核心对象

- **课程身份**：一门课程长期稳定的身份、归属和基本信息。
- **课程设计依据**：学生起点、学习目的、学科要求、课程类型、资料、模板、课时和教学条件。
- **课程内容与教学资产**：课程正文、课程知识、大纲、教案、讲义、题目、评价标准、教学日历和演示课件。
- **课程发布版本**：指向一组确定课程内容和教学资产修订的版本清单，不复制第二份课程正文。
- **教学实施**：某学期、某班级、某位教师和一组学生真实使用某个课程发布版本的教学安排。
- **教学场次**：教学实施中的某次课堂，绑定具体讲次和实际使用的教学资产。
- **学习事实与教学事实**：课堂、阅读、笔记、问答、作答、作品和教师观察中真实发生的事情。
- **教学解释与调整候选**：对事实的解释，以及面向个人、班级或公共课程提出的调整建议。
- **修订、回执与效果结论**：教师确认后的正式改变、实际执行结果、恢复记录和后续验证结果。

### 1.4 产品核心价值

```text
结构化同源
+ 教师可控的智能协作
+ 明确的发布与教学实施
+ 真实教学和学习证据
+ 可验证的课程生长
```

结构化同源保证不同教学材料服务同一门课程；教师可控保证人工智能只在授权范围内生成和修改；发布与教学实施保证学生使用的是明确版本；真实证据保证课程调整来自实际教学与学习；效果验证判断一次调整究竟改善了学习，还是需要缩小、撤销或重做。

### 2.2 完整产品运行图

完整图按九个执行区展开。九区不是九套系统，也不等于九个页面；它们是同一门课程从设计到生长的连续运行过程。

图中的加号表示多项信息共同成为下一步输入；“教师决定”表示产品必须等待，不能替教师继续；“当前可用”表示某项内容现在能够用于教学，不等于已经向学生发布。

#### 2.2.1 贯穿九区的内容形态与状态

课程内容可以由教师直接编辑、教师主动启动首次生成，或者由人工智能针对已有内容提出修改。三种入口最终都进入同一套内容形态：

```text
 [教师直接创建或编辑]   [教师主动启动首次生成]   [人工智能修改已有内容]
          |                       |                        |
          |               结果通过硬性检查                v
          |                       |                [人工智能修改候选]
          |                       |                        |
          |                       |                 教师采用或拒绝
          |                       |                        |
          +-----------+-----------+------------------------+
                      |
                      v
[课程当前工作修订]
          |
  结构、来源和质量检查
          |
          v
[当前可用教学资产]
          |
  选择修订、使用范围和生效时间
          |
          v
[课程发布版本]
          |
  某次教学实施明确采用
          |
          v
[教学实施实际使用版本]
```

五种形态承担不同责任：

| 内容形态 | 含义 | 不能被误解为什么 |
| --- | --- | --- |
| 人工智能修改候选 | 人工智能针对已有内容提出的待审阅改变 | 已经修改正式课程 |
| 课程当前工作修订 | 教师正在维护的当前课程内容或教学资产 | 已经向学生发布 |
| 当前可用教学资产 | 结构完整、来源可接受、能够用于教学的当前修订 | 所有教学实施必须立即切换 |
| 课程发布版本 | 指向确定课程正文与资产修订的不可变版本清单 | 复制出来的第二份课程正文 |
| 教学实施实际使用版本 | 某个学期和班级当前明确采用的发布版本 | 课程仓库中最新的任意修订 |

“课程当前工作修订”表示各课程对象当前可编辑修订的集合，不是另一份课程，也不改变每个对象原有的唯一真源。

内容形态之外，任务、来源、审阅、可见范围和效果必须分别保存，不能压成一个“状态”：

```text
内容形态：缺失 / 候选 / 工作修订 / 当前可用 / 已发布 / 已退役
任务状态：未启动 / 排队 / 运行 / 等待补充 / 等待审阅 / 暂停 / 取消 / 失败 / 完成
来源状态：当前有效 / 已经变化 / 无法确认
审阅状态：无需审阅 / 待审阅 / 已采用 / 已拒绝 / 已撤销
可见范围：仅教师 / 指定实施 / 指定班级 / 指定学生
效果状态：未验证 / 初步支持 / 稳定确认 / 证据不足 / 无效 / 有害
```

一次任务失败，只能改变本次任务和最近尝试，不能自动把最后可用教学资产、已发布课程版本或正在进行的教学实施判为失败。

## 3. 覆盖整张运行图的共同规则

### 3.1 每次生成都先固定本次依据

```text
[当前上游修订]
+ [本次生成范围]
+ [资料修订和作用范围]
+ [教师补充要求]
+ [内容模板和学科标准]
+ [目标教学产物]
                  |
                  v
          [不可变生成依据]
                  |
                  v
             [本次任务]
```

任务开始后的资料上传、教师编辑和规则变化只参与下一次生成，不能污染正在运行的任务。

### 3.2 批量启动，按最小单元分别恢复

```text
教师点击生成全部
-> 只选择缺失、过期或明确需要重做的讲次
-> 每讲建立独立任务
-> 所有任务一次进入队列
-> 在统一容量下处理
-> 每讲分别保存进度
-> 每讲分别成功或失败
-> 重试只处理失败或缺失讲次
```

批量生成不等于整批共同成败，不要求前一讲完成后才开始后一讲，也不因为一讲失败而清空整门课程。

### 3.3 任务状态、资产可用性和学生可见性彼此独立

```text
最近一次任务失败
+ 上一份教学资产仍然可用
+ 已发布课程版本仍然有效
+ 教师可以查看原因或重试
```

只有新的工作修订通过相应检查并被明确发布后，学生可见内容才发生变化。教师预览当前工作修订不等于向学生发布。

### 3.4 一处变化先判断责任，再决定传播

```text
变化来源
-> 识别变化对象和适用范围
-> 找到真正负责的课程内容或教学实施
-> 分析影响范围
-> 形成调整候选
-> 相应责任人审阅
-> 正式应用
-> 精准更新受影响内容
-> 必要时形成新发布版本
-> 用后续独立结果验证
```

| 传播类型 | 产品处理 |
| --- | --- |
| 必须传播 | 上游已经明确变化，下游继续使用会产生错误或矛盾；相关内容必须进入处理状态 |
| 需要复核 | 产品知道某些内容可能受影响，但不能确定是否必须修改；向教师说明原因和范围 |
| 禁止自动传播 | 学生弱信号、人工智能推测、普通问答和未经确认的资料变化只形成候选，不改写课程 |

### 3.5 失败回到最近的合法阶段

| 当前情况 | 下一步 |
| --- | --- |
| 创建输入不足 | 回到具体字段，保留其他输入和已上传资料 |
| 等待教师补充 | 回到当前任务补充信息，然后继续原任务 |
| 等待教师审阅 | 进入对应审阅，不能使用普通继续替代决定 |
| 已暂停 | 从原任务检查点继续 |
| 已取消 | 保留取消事实；再次生成时建立新任务 |
| 可恢复失败 | 只重试失败或未完成单元 |
| 来源已经变化 | 保留旧可用结果，按最新来源建立新的生成尝试 |
| 内容修改发生冲突 | 回到影响和冲突审阅，不直接覆盖 |
| 状态无法确认 | 只允许查看原因，禁止猜测继续 |
| 服务中断或页面刷新 | 根据任务身份和检查点恢复，不重新建立同目标任务 |
| 发布检查未通过 | 保留工作修订和旧发布版本，返回具体问题对象 |
| 教学实施切换版本失败 | 继续使用原版本，不产生部分学生已切换的假象 |
| 效果证据不足 | 继续观察，不宣布调整有效或失败 |

## 5. 图中必须守住的产品边界

1. 课程是产品中心，大纲、教案、讲义、题目和课件只是同一课程面向不同教学任务形成的资产。
2. 一门课程只有一份课程正文；发布版本通过修订引用固定内容，不复制第二份课程正文。
3. 课程、课程发布版本和教学实施是三个不同对象：课程可以持续修改，发布版本不可变，教学实施明确采用某个版本。
4. 教师预览当前工作修订，学生读取教学实施采用的发布版本；二者不能以同一个“最新课程”代替。
5. 任务状态、资产可用性、来源新鲜度、教师审阅、学生可见性和效果结论是不同状态维度。
6. 每讲独立生成、独立成功、独立失败和独立恢复；一讲失败不能清空整门课程。
7. 上游变化先分析影响、保护不变项并保留旧版本，再由教师决定是否更新。
8. 学习事实、教学解释、调整候选和正式改变必须分开。
9. 个体补救、班级实施调整和公共课程改进必须分别判断证据范围和写入目标。
10. 人工智能负责理解、生成、分析和提出候选；教师拥有课程和教学实施的最终决定权。
11. 调整应用成功只证明产品完成了修改，不证明教学已经改善。
12. 效果结论必须绑定调整对象、适用范围、基线、独立任务、课程版本和教学实施。

## 6. 三层设计怎样闭合

本章不增加新的教学对象或产品模块，而是检查前三层能否逐项对应。

### 6.1 内容对象、产品机制与界面载体

第一层中的每个教学对象都必须回答：

```text
它是什么
-> 由什么形成
-> 谁能够修改
-> 怎样成为当前工作修订
-> 怎样满足当前可用条件
-> 是否需要进入课程发布版本
-> 在哪次教学实施中被使用
-> 会影响哪些对象
-> 用户在哪里看见和操作
-> 失败后怎样恢复
```

如果一个内容模板在第二层没有形成、修改、使用和验证机制，它仍然只是文档模板；如果一个产品机制在第三层没有入口、过程、状态和决定方式，它仍然只是后台能力。

### 6.2 教师端与学生端同源

- 同一个课程目标在教师端表达为教会什么和怎样检查，在学生端表达为学会什么和怎样证明。
- 同一讲形成教案、讲义、演示课件和学生学习内容，但只有一份课程语义和正式来源。
- 学生端不得复制独立课程正文，而应通过教学实施读取确定的课程发布版本。
- 教师预览复用真实学习界面，但读取范围和身份必须明确标记为教师预览。

### 6.3 人工智能与正式结果的边界

```text
人工智能输出
-> 可审阅候选
-> 有权责任人决定
-> 工作修订或实施调整
-> 执行结果
-> 必要时形成发布版本
-> 撤销与恢复
```

这些步骤不能混成一个“生成成功”。人工智能可以提出改进、解释影响和执行受控动作，但不能替用户确认、扩大范围或隐藏失败。

### 6.4 变化传播的一致性

- 上游变化通过真实来源和依赖找到下游。
- 受影响内容进入复核或局部重建，不受影响内容明确保留。
- 普通质量建议只产生建议，硬性错误才阻断使用或发布。
- 新结果生成失败时，最后可用结果和旧发布版本继续存在。
- 更新完成后通过新的教学或学习证据重新验证。

### 6.5 跨层硬边界

- 页面不能另建一套产品事实。
- 导出文件不能反过来成为课程真源。
- 学习位置不能冒充掌握证据。
- 学生弱信号不能直接改写公共课程。
- 课程最新修订不能自动替换正在进行的教学实施。
- 技术字段、接口和存储方式不进入本产品逻辑正文。

## 7. 完成标准

### 7.1 产品机制完成标准

- 九个执行区都有输入、处理、决定、结果和返回路径。
- 工作修订、当前可用、课程发布和教学实施版本的关系明确。
- 批量、局部、失败、恢复和变化传播规则完整。
- 教师、学习者、教务管理者、人工智能和系统的权力边界清楚。
- 个体、班级和公共课程三种调整不会互相越界。
- 学习证据能够进入相应调整，并接受独立效果复验。

### 7.2 整体产品完成标准

```text
教师能够完成课程设计
-> 系统能够形成同源教学产物
-> 教师能够选择内容并发布课程版本
-> 学期和班级能够建立明确教学实施
-> 教师能够真实教学
-> 学生能够在确定版本中真实学习
-> 系统能够获得可追溯证据
-> 相应责任人能够据此调整个人、实施或课程
-> 后续独立学习能够验证调整效果
```

只有这条链真实成立，灵知才从课程内容生产系统成为完整的智能课程系统。
