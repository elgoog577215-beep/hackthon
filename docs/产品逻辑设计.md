# 灵知产品逻辑设计

本文定义灵知是什么，以及教学内容怎样在产品中创建、生成、修改、使用、失败、恢复和继续生长。教学内容本身由《教学内容设计》负责，用户怎样参与由《交互与界面设计》负责，具体实现由《系统架构》负责。

## 1. 灵知是什么

### 1.1 灵知处理的核心问题

灵知需要共同解决四个问题：

1. 教师怎样把教学设想转化为完整、专业、可以实施的课程。
2. 大纲、教案、讲义、题目、教学日历和演示课件怎样保持同源。
3. 教师教学和学生学习产生的真实证据怎样反过来改善课程。
4. 人工智能怎样参与课程设计、内容生产和课程修改，同时保留教师的决定权。

### 1.2 核心用户及其真实任务

- **教师**设计课程、准备教学、实施课堂、检查学习结果并调整课程。
- **学习者**理解课程内容、完成学习任务、记录问题、获得帮助并证明掌握。
- **课程设计者**维护课程结构、教学标准、内容模板与正式材料。

### 1.3 灵知管理的核心对象

- 一门持续生长的正式课程。
- 课程的教学设计、知识体系和资料来源。
- 大纲、教案、讲义、题目、教学日历、评价标准和演示课件。
- 教师教学过程、学生学习过程与学习证据。
- 根据证据形成的课程调整方案和新课程修订。

### 1.4 产品核心价值

```text
结构化同源
+ 教师可控的智能协作
+ 真实学习证据
+ 可验证的课程生长
```

结构化同源保证同一门课程的不同教学材料不会各自生长；教师可控保证人工智能只能提出候选、解释影响和执行经过授权的动作；真实学习证据让课程调整建立在实际教学与学习之上；效果验证判断一次调整究竟改善了学习，还是需要缩小、撤销或重新设计。

### 1.6 产品最终形成的结果

- 教师得到一套可以直接使用和持续维护的课程。
- 学习者得到与教师课程同源的学习体验。
- 每一次生成、修改和调整都有依据、影响范围和恢复方法。
- 课程是否改善最终由新的教学与学习证据判断。

本稿采用“图是正文，文字是注释”的组织方式。

## 3. 覆盖整张运行图的共同规则

### 3.1 每次生成都先固定“本次生成依据”

本次生成依据包括：

- 当前使用的上游内容版本；
- 本次选择的讲次范围；
- 本次使用的资料及其版本；
- 每份资料适用于哪些讲次；
- 教师本次补充的要求；
- 当前内容模板；
- 当前学科标准；
- 当前要生成的教学产物。

生成开始后，即使教师又上传资料或修改要求，也不能污染正在运行的任务；新的变化进入下一次生成。

### 3.2 批量启动，按最小单元分别恢复

~~~text
教师点击生成全部
-> 产品只选择缺失、过期或明确需要重做的讲次
-> 每讲建立独立任务
-> 所有任务一次进入队列
-> 在统一容量下同时处理
-> 每讲分别保存进度
-> 每讲分别成功或失败
~~~

批量生成不等于整批共同成败：

- 成功的讲次立即保留。
- 失败的讲次单独显示。
- 重试只处理失败或缺失讲次。
- 不要求前一讲成功后才能开始后一讲。
- 不因为一讲失败清空整门课程。

### 3.3 任务不能只有“完成”和“失败”

~~~text
未生成
-> 等待处理
-> 正在生成
-> 生成成功

正在生成
-> 等待教师补充
-> 等待教师审阅
-> 已暂停
-> 已取消
-> 生成失败
~~~

| 当前情况 | 下一步 |
| --- | --- |
| 等待教师补充 | 回到当前任务补充信息，然后继续原任务 |
| 等待教师审阅 | 进入对应审阅，不能使用普通继续 |
| 已暂停 | 从原有检查点继续 |
| 已取消 | 保留取消事实；需要生成时重新创建任务 |
| 可恢复失败 | 只重试失败或未完成单元 |
| 内容已经变化导致冲突 | 回到冲突处理，不能直接重试 |
| 状态无法确认 | 只允许查看原因，不能猜测继续 |
| 最近一次重新生成失败，但旧版本可用 | 继续展示旧版本，同时提示最近一次失败 |
| 服务中断或页面刷新 | 根据正式任务状态和检查点恢复，不重新生成 |
| 人工智能服务暂时不可用 | 保留现有课程和最后可用结果，恢复后继续任务 |

### 3.4 最后可用结果永远优先保留

如果教师已经有一份可用讲义，再次生成失败，产品状态应当是：

~~~text
当前讲义仍然可用
+ 最近一次重新生成失败
+ 可以查看原因或重试
~~~

而不是把整份讲义显示成“生成失败”。同样的原则适用于教案、题目和演示课件。

### 3.5 一处变化先判断责任，再决定传播

~~~text
变化来源
-> 识别变化类型
-> 找到真正负责的课程内容
-> 分析影响范围
-> 形成调整候选
-> 教师审阅
-> 正式应用
-> 精准更新受影响内容
-> 用后续学习结果验证
~~~

变化传播分为三类：

| 传播类型 | 产品处理 |
| --- | --- |
| 必须传播 | 上游已经明确变化，下游继续使用会产生错误或矛盾；相关内容必须进入处理状态 |
| 需要复核 | 产品知道某些内容可能受影响，但不能确定是否必须修改；向教师说明原因和范围 |
| 禁止自动传播 | 学生弱信号、人工智能推测、普通问答和未经确认的资料变化，只形成候选，不改写课程 |

## 5. 图中必须守住的产品边界

1. 课程是产品的中心，不是大纲、教案、讲义或演示课件中的任何一份文件。
2. 大纲、教案、讲义、题目和演示课件是同一门课程面向不同教学任务形成的不同成果，不是互相复制的五套课程。
3. 生成不是从头跑到尾的黑箱，而是由可观察、可暂停、可恢复的小任务组成。
4. 每一讲应当独立生成、独立成功、独立失败和独立恢复；一讲失败不能清空整门课程。
5. 失败应当回到最接近问题的合法阶段，不能把教师送回课程起点。
6. 上游变化不能自动覆盖下游；产品先判断影响、保护不变项并保留旧版本，再由教师决定是否更新。
7. 学习事实、教学解释、调整建议和正式课程变化必须分开。
8. 人工智能负责理解、生成、分析和提出候选；教师拥有最终教学决定权。
9. 调整应用成功只代表产品完成了修改，不代表教学已经改善；有效性必须由新的独立学习证据证明。

## 3. 三层设计怎样闭合

本章不增加新的教学对象或产品模块，而是检查前三层能否逐项对应。

### 3.1 内容对象—产品机制—界面载体对照

第一层中的每个对象都必须回答：

```text
它是什么
-> 由什么形成
-> 谁能够修改
-> 怎样成为当前结果
-> 影响哪些对象
-> 用户在哪里看见和操作
-> 失败后怎样恢复
```

如果一个内容模板在第二层没有形成、修改和使用机制，它仍然只是文档模板；如果一个产品机制在第三层没有入口、过程、状态和决定方式，它仍然只是后台能力。

### 3.2 教师端与学生端同源

- 同一个课程目标在教师端表达为教会什么和怎样检查，在学生端表达为学会什么和怎样证明。
- 同一讲内容形成教案、讲义、演示课件和学生学习页面，但只有一份课程语义和正式来源。
- 学生端不得复制一份独立课程正文。
- 教师预览复用真实学习路径，不另建展示版本。

### 3.3 人工智能与正式结果的边界

```text
人工智能输出
-> 可审阅候选
-> 教师决定
-> 正式课程修订
-> 执行结果
-> 撤销与恢复
```

六者不能混成一个“生成成功”。人工智能可以提出改进、解释影响和执行受控动作，但不能替用户确认、扩大范围或隐藏失败。

### 3.4 变化传播的一致性

- 上游变化通过真实来源和依赖找到下游。
- 受影响内容进入复核或局部重建，不受影响内容明确保留。
- 普通质量建议只产生建议，硬性错误才阻断使用。
- 新结果生成失败时，最后可用结果继续存在。
- 更新完成后通过新的教学或学习证据重新验证。

### 3.5 跨层硬边界

- 一门课程只有一份正式正文。
- 学习事实与人工智能判断分开保存和表达。
- 教师决定不能被人工智能代替。
- 页面显示状态不能另建一套产品事实。
- 导出文件不能反过来成为课程真源。
- 学习位置不能冒充掌握证据。
- 技术字段、接口和存储方式不进入三份产品设计文档正文。

## 4. 完成标准

### 4.1 产品机制完成标准

- 九个执行区都有输入、处理、决定、结果和返回路径。
- 批量、局部、失败、恢复和变化传播规则完整。
- 教师、学习者、人工智能和系统的权力边界清楚。
- 学习证据能够进入课程调整并接受独立效果复验。

### 4.2 整体产品完成标准

```text
教师能够完成课程设计
-> 系统能够形成同源教学产物
-> 教师能够真实教学
-> 学生能够真实学习
-> 系统能够获得可信证据
-> 教师能够据此调整课程
-> 后续学习能够验证调整效果
```

只有这条链真实成立，灵知才从课程内容生成工具成为完整的智能课程系统。
