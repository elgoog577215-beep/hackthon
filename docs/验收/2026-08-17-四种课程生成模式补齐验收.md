## 三、关键验收点：两种新模式是否真的改变生成行为

这是本次验收的**核心问题**。只加类型枚举、前端多个按钮，但生成链路走同一套规则，
等于没补齐——而且比没补更糟，因为看起来像有。

差异化由 `course_prompt_composer.py:33` 的 `_course_type_planning_rules()` 驱动，
它按 `course_type` 与合同里的 `required_planning_stages` 产出**不同的目录规划规则**。

实测四种类型的合同内容：

| 类型 | 是否启用 | 教学目的 | 必经规划阶段 |
|---|---|---|---|
| systematic | ✅ | systematic | 0（**按设计**：目录按知识先修关系推进） |
| project | ✅ | systematic | 0（**按设计**：用里程碑与路径角色表达，不用阶段） |
| inquiry | ✅ | systematic | **5**：define_question → decompose_questions → gather_evidence → test_explanations → form_conclusion |
| exam | ✅ | **exam_sprint** | **5**：scope_diagnosis → priority_review → targeted_practice → mock_assessment → final_consolidation |

**两个 0 不是遗漏，是两条不同的差异化路径**，代码里写得很明确：

- `project` 命中 `_course_type_planning_rules` 的专属分支（第 37-41 行），
  有自己的路径角色规则：起点不足时不得用 `compressed`、未证实能力用 `verify_in_project`、
  阶段成果用 `milestone`，且 `planning_stages` 显式要求为空数组。
- `systematic` 走兜底分支（第 51-53 行），显式声明"`planning_stages` 使用空数组，
  目录按知识先修关系推进"，并禁止出现项目专属角色。
- `inquiry` / `exam` 走 `required_stages` 分支（第 42-50 行），
  生成的规则要求"每章必须填写 `planning_stages`，只允许使用这 5 个 id，
  必须全部覆盖并按给定顺序推进，不得倒序"。

另外 `exam` 的 `purpose` 是唯一一个不等于 `systematic` 的（`exam_sprint`），
说明它在下游还有独立的组织方式，不只是目录层不同。

## 五、诚实边界

1. **本次是静态核查 + 单元测试，没有对 inquiry / exam 各真实生成一门完整课程。**
   合同、前端入口、提示词规则三层都对得上，但"模型是否真的按这 5 个阶段产出目录"
   需要真机跑一次才能下定论。**服务器恢复后建议各跑一门补上这一条。**
2. 生成阶段的规则是**写进提示词**约束模型的，属于软约束。
   `planning_stages` 是否被校验层强制，本次没有追到底。
3. project 与 systematic 的 `required_planning_stages` 都是 0，
   两者的区分完全依赖 `_course_type_planning_rules` 里的分支——
   这一段没有单独的回归测试钉住，改动时容易误伤。**建议补一条。**
