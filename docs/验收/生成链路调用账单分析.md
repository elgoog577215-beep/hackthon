# 生成链路调用账单分析（A-2）

> 数据来源：A-1 埋点产出的 JSONL 账单，**两次真实跑一门 8 课时课程**
> （主题「线性代数入门」，`total_class_hours=8`、`section_count=8`），
> 打到真实模型端点 `221.12.22.187:30938`（自部署千问 `qwen3.6-35b-a3b`）。
> token 数是 **provider 通过 `stream_options.include_usage` 返回的真实计数**，
> 不是估算。分支 `dev/lz-perf`，基准 `7b474a99`。

## 摘要：先看这一条

**四个嫌疑里，第 4 条（失败恢复时已完成产物被重新编译）是主因，
它同时是第 1 条（上下文重复发送）的成因。第 2 条不成立——教案批次数是 4，
不是"过多"。第 3 条本轮两次运行都没跑到练习阶段，无实测数据，
但 A-3 已从代码侧给出确定结论。**

换句话说：**要压时间，先修「重试重跑已完成批次」这一条，不要去拆批次。**

## 嫌疑逐条结论

### 嫌疑 1：同一份上下文被多次重复发送 —— **成立，且量级很大**

**实测数字：运行① 55 次调用里只有 20 个不同的 prompt，49 次调用携带的是
重复 prompt；按「同一 prompt 第 2 次及以后都算浪费」计，
浪费 125,994 / 188,177 = 67.0% 的输入 token。运行② 为 53.4%。**

重复不是"部分上下文相同"，而是 **prompt 逐字节完全相同**（SHA 一致）。
典型重复组（运行①）：

| prompt 指纹 | 发送次数 | 每次输入 token | 出现在第几次调用 |
| --- | ---: | ---: | --- |
| `5d01d74f1500cc55` | 5 | 5,121 | 15, 28, 29, 35, 51 |
| `588935e3e19894a3` | 5 | 5,893 | 16, 26, 38, 40, 53 |
| `d8744324d819d1ab` | 4 | 5,310 | 13, 27, 36, 52 |
| `ef34ff4f7f68d9f6` | 4 | 5,273 | 14, 25, 37, 50 |
| `57ed01ce8c212596` | 4 | 2,073 | 6, 20, 30, 45 |
| `4e1cefc18783af0b` | 4 | 2,236 | 7, 22, 32, 42 |
| `a7c4055a3eba6d23` | 4 | 2,178 | 8, 19, 33, 43 |
| `0f183bfef7d0ee4a` | 4 | 2,355 | 9, 21, 31, 44 |

**注意重复的位置分布**：不是连续两次（那会是普通重试），而是分散在 4 个
互相远离的区段。这正是"整轮重跑"的指纹，见嫌疑 4。

> ⚠️ 所以嫌疑 1 **不是一个独立的病**，它是嫌疑 4 的症状。
> 单独去做 prompt 瘦身或前缀缓存，治不了根。

### 嫌疑 2：教案拆成过多批次 —— **不成立**

**实测数字：8 节课的教案只切成 4 个批次。**运行① 里输入 >4000 token 的
"教案批次级"调用共 18 次，但**只有 4 个不同的 prompt**——18 次是 4 个批次
被重跑了 4~5 轮的结果，不是切了 18 个批次。

小于 4000 token 的小节级调用 37 次，对应 **16 个**不同 prompt。

结论：**批次粒度本身没问题，不需要合并批次。** 看起来"批次很多"是重跑
造成的假象。lz-lesson-plan 不需要为"减少批次数"动手。

### 嫌疑 3：练习走"逐题生成—逐题检查—逐题修复" —— **本轮无实测数据**

两次运行都在**教案阶段就失败了，没有进入练习阶段**
（`services` 全部是 `CourseService`，没有 `AssessmentOrchestrator` 的记录）。
所以我不能用本轮账单给这条嫌疑下"成立/不成立"。

**但 A-3 已从代码侧给出确定结论，且与这条嫌疑一致**：练习修复确实是
逐条发请求——批量函数被调用了，但每批只有 1 个候选。详见
`NOTES_TO_OWNER.md` 的 A-3 段落。要点：

- 修复 12 次、独立求解 18 次，**都是每次一个候选**；
- 最大头是独立求解（deliberate 档 `solution_batch_size=1`，批量完全没开），
  不是修复。

**这条要拿实测数字，得先让教案阶段能过（即修嫌疑 4），或者单独跑练习链路。**

### 嫌疑 4：失败恢复时已完成产物被重新编译 —— **成立，是主因**

**机制（精确行号）**：`course_service.py:2782-2811`，教案语义门没过时，
`_prepare_course_teaching_plan` **递归调用自己**：

```python
if fallback_units:
    if semantic_retry_count < _semantic_retry_budget():   # :2783
        ...
        return await self._prepare_course_teaching_plan(  # :2805 递归
            course_data=course_data,
            plan=plan,
            artifacts=artifacts,
            semantic_retry_count=semantic_retry_count + 1,
        )
    raise AIProviderRequestError(                          # :2813
        "全课教案仍有非 AI 语义单元，已保留成功批次并停止在正文之前；..."
    )
```

重试预算默认 **3**（`_semantic_retry_budget`，`course_service.py:222-235`），
所以最多 1 + 3 = 4 轮——**与账单里观察到的 4 轮重复精确吻合**。

**关键矛盾**：`_semantic_retry_budget` 的文档字符串（`:225-226`）声称

> "A retry only re-runs the batches that fell back to local compilation,
> so each extra pass is cheap."

**这句话与实测不符。** 如果只重跑失败批次，账单里不会出现
"已经 `completed` 的 prompt 又被逐字节重发 3 次"。骨架（skeleton）确实有
复用门（`skeleton_is_current`，`:2052-2068`），**但批次级没有等价的复用门**。

**代价（实测）**：运行① 的 795 秒墙钟里，
第 1 轮 18 次调用用了 375 秒忙时，之后 3 轮又打了 37 次调用、约 1,089 秒忙时
——**约 2/3 的教案阶段时间花在重算已经算对的东西上**，最后仍然失败。

## 排队 vs 忙时：B-4 的前置结论

| 指标 | 运行① |
| --- | --- |
| 墙钟 | 795 秒 |
| 忙时（各次调用耗时之和） | 1,464 秒 |
| **排队等待合计** | **5.4 秒** |
| 排队原因 | `start_interval` 27 次，其余为 0 |

**当前这套配置下排队几乎不存在（5.4 秒 / 795 秒 = 0.7%）**，唯一的等待来源是
容量控制器的发车间隔（`AI_PROVIDER_START_INTERVAL_SECONDS`，默认 0.1 秒）。

有效并行度 = 1464 / 795 ≈ **1.84**。也就是说 8 节并行阶段实际只跑出不到 2 路
并发，而 `AI_PROVIDER_INITIAL_CONCURRENCY=4`、`MAX=16`。
**并发没有被队列压住，是编排本身没有把并行度提上去。**

> ⚠️ 但任务书已说明：C-0（正式 API 通道）预计 8/20 到位，
> **在那之前测出来的容量是假的**。上面这组数字只用于说明
> "本轮的瓶颈不在排队"，不足以作为 B-4 的调参依据。B-4 仍应等 C-0。

## 顺带发现：两次输出截断触发整批重试

运行① 有 2 次失败，都是 `模型输出达到硬上限：max_tokens=16000`
（chars 23,344 / 22,763）。`_call_llm` 会加倍 `max_tokens` 后重试
（`ai_base.py` 的 `reject_truncated` 分支），第 2 次成功。

这不是本轮四个嫌疑之一，但它说明教案批次的输出规模已经贴着 16k 上限，
**批次再合并会更容易截断**——这是另一个"不要合并批次"的理由。

## 这份分析的边界（如实说明）

1. **嫌疑 3 没有本轮实测数字**，用的是 A-3 的代码侧结论。要实测得先让教案
   阶段能过。
2. 两次运行**都在教案阶段失败**，所以**正文阶段（14 分 35 秒）与练习阶段
   的账单本轮拿不到**。任务书基线里的那几个数字本轮没有复测。
3. 「重复浪费 token」的口径是「同一 prompt 第 2 次及以后的输入全算浪费」。
   如果将来接入 provider 前缀缓存，这部分不会全额转化为成本节省，
   但**墙钟时间的浪费是实打实的**（重跑要重新等模型生成）。
4. 当前跑在自部署千问上，**不是 C-0 的正式通道**，绝对耗时不可外推。
   本文件里的**比例**（67%、53.4%、0.7%、1.84）比绝对秒数更可信。
