## 1. G-1 关系密度

### 改了什么（以及最后留下了什么）

试的是 `course_prompt_composer.py` 批次 prompt 约束 7 的两处：

1. **逐点覆盖要求**——本节每个新知识点至少出现在一条关系里（`source_key`
   或 `target_key` 都算），提交前逐个键点名核对；确实孤立的才允许缺席。
   **→ 实测未通过，已撤回（`a3e1cf68`）。**
2. 原收尾"自查后确实不成立就留空，宁缺毋滥；本节只有两三个知识点时没有
   这几类是正常的"→ 改成"**某一类没有 ≠ 整节没有关系**"。
   **→ 保留。** 原文连起来读确实是一句可以被读成"点少可以不写关系"的许可，
   这是独立成立的问题，与密度是否改善无关。

**为什么当初不写"每节至少 N 条"**：条数下限会诱导模型编造关系凑数，而
`_compile_relations` 只校验必填字段、不校验教学正确性，编出来的边会直接进
知识网。按知识点覆盖天然挂在真实结构上，且保留了"确实孤立"的出口。

常驻检查：`tests/test_course_prompt_relation_contract.py` 保留 1 条
（`test_constraints_do_not_license_an_empty_relation_set`，锁第 2 项）。
锁第 1 项的那条随撤回一并删除——不留断言去锁一段已经不存在的文字。


### 实测数字

同一门课、同一 provider、同一需求文件，唯一变量是上面那段 prompt。

| 指标 | 改前 | 改后 | 判定 |
| --- | --- | --- | --- |
| 关系条数 | 12 | **11** | 未改善 |

| 零关系小节 | 4 / 6 | **4 / 6** | 未改善 |

改前类型分布：`prerequisite 5、applies_to 3、contrasts_with 3、derives 1`
改后类型分布：`prerequisite 6、contrasts_with 3、derives 2`

**结论：这条 prompt 改动没有验证成功，方向还是负的。**
我不把它包装成"落在噪声范围内"——单次对照本来就不足以判定有效，
而唯一这一次的结果是变差。**是否保留由你定**（见文末待拍板第 1 条）。

### 但这两次跑出了一个更值得追的现象

**两次零关系的是同样的 4 节，不是随机的 4 节：**

| 小节 | 改前 | 改后 |
| --- | --- | --- |
| L2-1-1 | 0 | 0 |
| L2-1-2 | 0 | 0 |
| **L2-1-3** | **5** | **5** |
| L2-2-1 | 0 | 0 |
| L2-2-2 | 0 | 0 |
| **L2-2-3** | **7** | **6** |

有产出的恰好是**每章最后一节**，两次都是。这不是模型波动。

**而且不是代码缺陷。** 3.12 那次（DeepSeek）的 `probe2.json` 里 6 节
**全部**有产出（1/1/2/1/7/3），零关系小节 0 个——同一套代码、同一门课。

所以这是 **claude-opus-5 特有的行为**：它把一个批次内所有小节的关系
**集中挂在批次最后一节**上。批次按章切（3 节一批），于是表现成
"每章只有最后一节有关系"。

**这也解释了为什么加覆盖要求没用**：模型并没有漏找关系，它找了，
只是全写在一节里。逐点覆盖要求约束的是"找不找"，管不到"写在哪一节"。

影响有两处，都指向教师界面：
- 前 2/3 的小节里教师看不到任何知识联系；
- `teaching_batch:relation_diversity_low` 会对那些小节持续误报。

## 2. G-2 知识点来源绑定

### 问题的实际形态

改之前知识点的 `source_refs` 只有一个来源：`_section_evidence_refs()` 读的
**小节级** `evidence_refs` / `grounding_contract`。粒度是小节，后果两个方向都不如实：

- 小节挂了资料 → 该节**所有**知识点都记成"有依据"，但没有任何一条能回答
  "这个知识点的依据是哪一块"。落地率虚高。
- 小节没挂资料 → 知识点级来源恒空，落地率恒 0。

`evidence_package.py` 的 `evidence_for_keys()` 本来就是为这一层准备的
（docstring 写着"D1 第二层用"），但**在此之前没有任何生产调用方**，只有测试引用。

### 改了什么

`course_knowledge_base.py`：

- 编译期 `load_frozen_package(course_data)` 取冻结包，按知识点自己的
  **名字 + 别名** 调 `evidence_for_keys()` 取匹配证据，写进新字段
  `source_bindings`（带 `evidence_id / asset_id / origin / url / credibility`），
  并把 `evidence_id` 并进 `source_refs`。取不到就是空数组——不兜底。
- **只用名字与别名、不用 `statement`**：`_match_score` 是词面包含判断，
  `statement` 是整句话，拿它当键几乎所有证据都会命中，绑定就失去了
  "这一块讲的正是这个知识点"的含义。宁可少绑。
- `_web_evidence_ids()` 增加第二条判据：逐点绑定自带的 `origin`。
  逐点绑定直接来自冻结包的 `source_index`，不经过 `material_bindings`，
  只用原判据会把一条 license_unknown 的网页报成"教师上传资料依据"。
- `_source_grounding()` 增加 `point_bound_count` / `point_binding_ratio`。

前端：`frontend/src/types/knowledge-library.ts` 补 `KnowledgeSourceBinding`
与两个新字段（`npx tsc --noEmit` 通过，`knowledge-library.test.ts` 17 项通过）。

### 分母怎么算的

    point_binding_ratio = point_bound_count / knowledge_point_count

- **分母 `knowledge_point_count`**：编译后 `course_knowledge_base.knowledge_points`
  的条数，即这门课最终进知识网的原子知识点总数（不含概念组、能力点、易错点）。
- **分子 `point_bound_count`**：`source_bindings` 非空的知识点数，
  即**这个知识点自己**匹配到了至少一条证据。

刻意与 `grounded_ratio` **共用同一个分母**，两个比率可以直接对读：
`grounded_ratio` 的分子含小节级共享证据（小节粒度），
`point_binding_ratio` 的分子只含逐点匹配（知识点粒度）。
两者并列才看得出"这门课的资料到底细到哪一层"。

### 实测数字

真实上传资料（`/tmp/kb-gen/material_ac_dc.md`，1272 字教学资料节选）走完整
资料管线，冻结包 `evp_cbb799b4961ab50c`，**解析出 21 个证据单元**。

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| `knowledge_point_count`（分母） | 27 | 27 |
| `point_bound_count`（分子） | **0** | **4** |
| **`point_binding_ratio`** | **0** | **0.1481** |
| `material_grounded_count` | 0 | 4 |
| `web_grounded_count` | 0 | 0 |
| `course_generated_count` | 27 | 23 |
| 绑定来源 origin | — | `material` × 8 |

**落地率从 0 提到 0.1481（4/27）。** 改前是 0 不是因为代码没跑，而是因为
知识点级来源根本没有产出方——`evidence_for_keys()` 在此之前没有任何生产调用方。

绑上的 4 个：`直流电`（3 条证据）、`交流电`（3 条）、`脉动直流电`（1 条）、
`人体安全电压阈值`（1 条）。

### 0.1481 不高，原因是可解释的，不是随机的

看没绑上的 23 个知识点的名字就清楚了：

    正弦电动势瞬时值表达式 / 有效值的热效应等效定义 / 变压器的互感耦合工作原理
    理想变压器的电压比关系 / 高压输电降损原理 / 三孔插座地线接地要求 ...

**资料里明明写了变压器、有效值、电动势峰值、安全用电**，但这些知识点没绑上。
机制在 `evidence_package._match_score`：

```python
if normalized in compact or normalized in haystack:
```

判据是**知识点名字整体是否出现在证据文本里**。`直流电` 这种短名字能命中，
`变压器的互感耦合工作原理` 这种描述性复合名字**永远不可能**逐字出现在资料里。
所以绑定率实际上被"知识点命名风格"卡住了，而不是被资料覆盖度卡住。

这是**方向反了**：应该同时看"证据关键词是否出现在知识点名字里"。
`变压器的互感耦合工作原理` 含 `变压器`，反向匹配就能命中。

**我没有改它**，因为这条判据是上一轮**刻意**写保守的（`_match_score` 的
docstring：「只做词面包含判断，不做语义推断——宁可少绑，也不制造看不出依据的
绑定」）。放开反向匹配会让"有依据"的含义发生变化：`交流电` 这一条证据会连上
`交流电综合计算的量传递链`，那到底算不算依据是**产品判断**，不是我该单方面
改的。见文末待拍板第 5 条。

**所以 0.1481 是当前判据下如实的数字，不是这条链的能力上限。**

### 5. `_match_score` 的匹配方向（决定 G-2 落地率的上限）

见 §2。当前判据只看"知识点名字整体是否出现在证据里"，描述性复合名字
（`变压器的互感耦合工作原理`）永远命中不了，尽管资料里确实讲了变压器。

**建议改法**：在现有判据之外补一条反向包含——证据的 `keywords` 若出现在
知识点名字里也算命中。仍然是纯词面匹配、不引入语义推断，符合原设计的底线。

**为什么等你拍板**：放开后 `交流电` 这一条证据会连上
`交流电综合计算的量传递链` 这类知识点。那算不算"有依据"是产品判断——
判宽了会让 `material_grounded` 重新变成没有信息量的标签（这正是 D2 当初
要修的问题），判严了落地率就停在 0.15 左右。

需要你定的是**一句话的产品语义**：知识点级来源绑定要回答的是
"这一块资料讲的正是这个知识点"，还是"这一块资料与这个知识点相关"。
定了我就能把判据写准，并补上对应的常驻检查。
