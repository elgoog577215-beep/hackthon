# 灵知项目文档入口

> 文档状态：当前文档系统唯一入口<br>
> 本文只维护文档职责、阅读顺序和生命周期，不保存产品进度、实施任务或历史结论。

## 1. 最短阅读路径

新任务先判断自己要回答哪类问题，再进入对应真源：

| 问题 | 唯一入口 | 回答范围 |
| --- | --- | --- |
| 灵知是什么、哪些边界不能改变 | [产品总蓝图](./product-blueprint.md) | 产品定义、核心闭环、领域真源、用户旅程、边界与完成门 |
| 现在做到哪里、下一步攻什么 | [产品状态板](./product-status.md) | 当前成熟度、活动 OpenSpec、关键缺口、风险与攻坚顺序 |
| 整体按什么因果顺序建设 | [整体开发需求与依赖路线图](./requirements/灵知整体开发需求与依赖路线图.md) | `P0-P6` 前置依赖、完成门和禁止跨越项 |
| 当前领域合同在哪里 | [需求与领域合同入口](./requirements/README.md) | 稳定领域设计与活动 OpenSpec 规格的路由 |
| 代码现在怎样运行 | [架构文档](./architecture/) | 当前生产实现、接入位置、兼容和降级事实 |
| 某项高影响变更怎样施工 | [`openspec/changes/`](../openspec/changes/) | 提案、设计、正式需求、任务与验收 |
| 某条链是否真实通过 | [验收证据](./acceptance/) | 固定样本、执行记录、失败边界和历史验收结果 |
| 外部资料曾得出什么结论 | [研究快照](./research/) | 带日期的市场、源码和方案输入，不自动改变当前真源 |
| 为什么曾经这样决定 | [`docs/ai-memory/`](../../docs/ai-memory/) | 历史决策、错误与复用经验 |

## 4. 文档生命周期

```text
讨论与研究
-> 稳定产品判断进入蓝图或领域设计
-> 高影响实施进入 OpenSpec
-> 实现事实进入架构文档
-> 当前成熟度进入状态板
-> 验收结果进入验收证据
-> 被替代材料进入 archive
-> 历史原因进入 docs/ai-memory，时间线交给 Git
```

状态只允许以下四类：

| 状态 | 含义 | 允许更新什么 |
| --- | --- | --- |
| 当前真源 | 现在仍约束产品或项目 | 直接修改原位置，不能追加冲突结论 |
| 活动合同 | 正在实施且尚未归档 | 提案、规格、任务和验收证据 |
| 带日期快照 | 研究、评估或验收发生时的事实 | 补充证据边界，不改写为当前状态 |
| 历史归档 | 已完成、停止或被替代 | 原则上只修复链接与归档说明 |

## 5. 创建与维护门禁

1. 新建文档前先确认现有真源不能承载，并写明状态、日期、上位真源、适用范围和退出条件。
2. 产品定义只更新蓝图；整体状态只更新状态板；依赖顺序只更新路线图；任务只更新 OpenSpec。
3. 领域字段、接口和场景优先进入 OpenSpec 正式规格；不要再创建“产品+技术+进度+任务”混合交接长文。
4. 架构文档记录当前代码事实，必须能指向真实模块；不得保存每日测试数字和下一攻坚位置。
5. 研究与验收文档必须保留日期和证据边界，不用旧报告的“当前”覆盖新状态板。
6. 录屏、会议、Design QA 和一次性执行稿任务结束后归档，不长期占据 `requirements/`。
7. 新结论推翻旧结论时修改正式真源原位置；历史交给 Git 和项目决策，不在文末继续叠加修正。
8. 所有移动或归档必须修复本地链接，并通过 Markdown 渲染、OpenSpec 与 `git diff --check` 验证。
